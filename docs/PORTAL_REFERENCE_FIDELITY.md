## Comparison rubric

For each workflow inspect navigation, hierarchy, position/meaning, labels, grouping, validation, list/detail result, consequence and keyboard behavior. Record each row as matched documented behavior, supported approximation, educational enhancement, unsupported or unverified. Do not average these into an unmeasured fidelity percentage.

| Workflow              | Intended match                                                                                  | Approximation / enhancement                                                                                               | Explicit exclusions                                                                                   |
| --------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Shell/Home            | Global header/search/menu; services and recent resources; breadcrumbs and contextual commands   | Original AzureLab light theme/icons; persistent simulation badge and Learn/Understand routes                              | Authentication/account switching, Copilot, Cloud Shell, Marketplace and personalized Azure dashboards |
| Search/list           | Actual services/resources, local filtering and resource-detail navigation                       | Bounded local search, accessible keyboard result links; text/type/subscription filters                                    | Azure Resource Graph queries, online docs search, real subscriptions and saved filters                |
| Resource group        | Subscription/name/metadata Region, staged review, explicit Create, actual list and notification | Tags tab explains unsupported tagging instead of discarding entered values; domain naming/capacity errors                 | Tags persistence, locks/IAM/moves and cascade delete                                                  |
| Plan                  | Project scope, name, Linux OS, Region, review/create, actual properties                         | One named learning profile, no fake price/SKU/zone choice; deterministic custom policy feedback                           | Azure SKU catalog, pricing, zones, runtime capacity/health or autoscale                               |
| Web App               | Project details, app name, hosting plan, review/create and resource overview                    | Region/OS visibly derived from plan; standalone plan workflow first; unsupported runtime/publish operations explained     | Code deployment, DNS/hostname, runtime-stack validation, networking, monitoring and billing           |
| Operation history     | Real accepted/rejected operation inspection and notifications                                   | Deterministic sequence/revision instead of invented timestamps, duration/deployment animation; educational causal receipt | Full Azure Activity Log schema, audit identity and monitoring events                                  |
| Architecture/learning | Correct resource relationships and contextual inspect links                                     | Original live graph, responsibility comparison, source-backed theory and independent task                                 | Not Azure Portal built-in feature parity; diagrams are AzureLab educational additions                 |

Review human transfer: an Azure administrator should find the supported create/list/detail path without coaching; a beginner should explain metadata versus plan location and repeat the process in a lawful real-Portal environment later. Those exercises are planned, not performed by automated tests. Unknown current label/placement variants remain disclosed; no screenshot-only claim of professional fidelity.

## Implementing-agent disposition of the supported subset

This is a document-to-implementation comparison, not a live-tenant/pixel comparison or human transfer test. M = matched documented meaning/path; A = supported approximation; E = original educational enhancement; U = outside this implementation; ? = requires human/real-Portal comparison. Each judgement is scoped to the references above, reviewed 2026-10-24.

Run the walkthrough with an Azure administrator and a beginner. Record whether they locate the correct service/scope without coaching, explain why metadata does not host an app, diagnose the actual denial and distinguish configuration from deployment. A wrong mental model, hidden essential control, misleading success or inability to find the task is a release-blocking defect requiring iteration. Automated functionality and implementing-agent screenshots are supporting evidence, not that human sign-off.
The final list taxonomy follows [P11](SOURCE_REGISTER.md#portal-resource-taxonomy): management containers remain in their dedicated services/search/hierarchy; All resources lists actual plan/app instances. This is an explicit source-informed projection, not a claimed Resource Graph API implementation. Stable training IDs and world revisions replace full ARM paths/audit fields. Uncommitted form values and session recents are transient; saved resources and assessment drafts are restored. These differences remain part of the human fidelity review.
