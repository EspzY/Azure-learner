## Original mission manuscript and activity contracts

### A — Diagnose the dependency, not the icon (Benefits: reliability)

An internal dispatch service is reported unavailable. The operations handover contains a configured VM and its attachments, but no health probe or application test. First read the real VM's OS disk, NIC, subnet and VNet references. An attached disk is persistent storage for the configured guest; a NIC refers to a subnet, which belongs to a VNet. These are configuration relationships. They do not establish that the guest booted, routes work, or the dispatch application answers requests.

Use an existing VM, or explicitly create one through the ordinary supported form if inventory is empty. Select it as this mission's subject and inspect the actual VM/OS disk/NIC/subnet. The technical start ledger boundary is recorded even though this is an inspection mission: the UI labels an existing subject as reused, never newly created.

Now construct a separate teaching hypothesis: a serving path needs its VM, OS disk, NIC and subnet. Choose one or two paths; for a second path declare whether its subnet dependency is shared or independent. Every replica and successful path is a conceptual assumption, not an extra Portal resource or proof of traffic routing. Inject an explicitly hypothetical loss of the first path's OS disk, NIC or subnet. Predict the number of usable declared paths, run, then compare the exact input snapshot and result. A subnet loss can affect both paths if the dependency was shared; adding compute alone cannot remove that shared dependency. A loss of the first private OS disk does not imply loss of the second path's separate disk. No subscription or group choice provides physical redundancy.

Guided completion requires real attachment inspection, two different declared topologies and causal reflection. Recommend removing the relevant single dependency and validating the whole application path; neither this graph nor a successful hypothetical path proves end-to-end availability or an SLA. Independent variation requires analysing a different failure/topology combination and rejecting the claim that merely adding a VM guarantees availability. It remains independent conceptual application grounded in inspected configuration, not an availability test.

### B — Accepted by which rule? (Benefits: governance)

A publishing team needs a Web application in App Sandbox. A colleague proposes changing the group's metadata region to bypass a Web-resource location rule. Inspect the real subscription/group and actual custom policy before deciding. The policy is assigned to App Sandbox and targets supported Web plans/apps; it permits West Europe. Group metadata is a different property. Shared Sandbox is outside that assignment but does not satisfy the team's requested administrative context.

Explicitly attempt a new plan in App Sandbox outside the allowed Web location. Inspect the actual rejected operation: requested type/location, target group, assignment scope, unchanged revision and no added resource. Correct the resource location yourself; create an accepted plan in the same group and an app hosted on it. Existing groups may be reused; historical plans/denials cannot satisfy this mission's new-command boundary. Compare the rejected and later accepted receipts, not just two colored badges. Changing a group name or metadata region does not change the requested plan's location. An unrelated accepted command is not a correction.

The causal reflection must identify scope plus type plus location and explain that acceptance demonstrates only those supported checks. It is not an audit of code vulnerabilities, identity permissions, regulatory compliance or runtime health. Independent variation uses a changed organizational diagnosis and fresh rejection/correction after its own boundary; the exact requirements remain visible without step-by-step solutions. The added learning is a controlled denied/corrected comparison and evidence interpretation, beyond the earlier procedural Web creation lab. Application-setting maintenance belongs to mission D rather than duplicating it here.

### C — An operating system is a responsibility (Service Types: IaaS)

A document-conversion team maintains a Linux-native process and must manage guest packages. It needs the authored standard training profile (4 vCPU,8 GiB RAM), a separate32 GiB data disk and Shared Sandbox responsibility. Explain that vCPU/RAM describe an authored allocation, not measured processing throughput or a currently sold Azure SKU. A data disk is durable block storage; it is not RAM and is not the OS disk. The OS disk hosts the configured guest. IaaS is relevant because the workload needs guest control, while that choice retains patching, software, data and access duties.

Create the actual supported VM bundle after the mission boundary. Choose image/profile/data disk and a valid new or existing same-group/same-region subnet. Inspect VM, OS disk, data disk, NIC and subnet; use the existing graph/list to distinguish attachment, subnet membership and management membership. The accepted bundle receipt is atomic. A validation error creates none of its dependencies. Existing VMs may be inspected but cannot meet this new-build task.

Explain what was configured and what remains untested: no guest login, converter installation, packet delivery or availability measurement occurred. The original independent variation changes both guest and administrative/resource needs: a Windows-only small scheduled control process needs the authored2 vCPU/4 GiB profile and a32 GiB data disk in App Sandbox. It is not the old Windows/standard/data64 task. Both require a service/control decision and a disk/network/responsibility explanation, not only matching form fields.

### D — A saved setting is not a running application (Service Types: PaaS)

UI terminology qualification: this record's “Save draft” denotes the effect of **Apply in the edit dialog**; the existing Azure-like button is labelled Apply, not Save draft. **Apply on the Environment variables page** sends the real supported SetAppSettings command. New learner instructions name both control contexts explicitly.

A catalog team owns its Web code and wants Microsoft to manage the guest OS. Select a real Web App/plan pair or explicitly build one through supported controls. Inspect the group, derived location and explicit plan reference. Shared group membership alone does not host an app. Explain the PaaS choice against a VM requiring guest administration; custom guest kernel requirements would change the choice.

The team plans a maintenance window. In the guided staging context, edit the harmless fictional keys APP_ENVIRONMENT=staging and CATALOG_MODE=read-only. Save draft changes only the form. Before Apply, compare the actual last saved configuration/receipt. Apply sends SetAppSettings; inspect the real updated receipt and persisted values. Then restore CATALOG_MODE=standard in the same staging app through a second explicit Apply. Inspect the second receipt and compare ordered read-only→standard snapshots on the same app. Reload before Apply must not count an abandoned draft; reusing old saved values does not count as new work. This change-and-restoration investigation is distinct from the original one-shot settings task.

The keys are original teaching conventions, not built-in App Service switches. Customer code would have to consume them; AzureLab runs no code/restart. Real App Service passes app settings to application code and setting changes can restart applications; our simulator records configuration only. The team retains responsibility for correct values, code, data, access and validation.

The independent situation changes the operation and decision: two actual Web Apps share one real App Service plan but need different app configuration. The selected publication app needs a new production/standard Apply following an actually changed target draft. A different actual app on that same plan needs a new staging/read-only Apply. The learner must inspect both apps, plan, group and both new receipts and explain application scope versus hosting/management scope. There is no mandatory read-only→standard sequence on one app in this variant. Guided work on one app, old saved values, two different plans or two writes to the same ID cannot satisfy it. New independent decisions/reasons and specific distractor feedback test configuration isolation without claiming physical/runtime isolation or observed traffic. PM17 supports shared-plan compute; PM18 configures settings on a selected app. Qualified human transfer validation remains separate.

Draft/Apply presentation signals are not command evidence. Actual post-boundary receipts/final configuration and explicit inspections determine completion.

The changed independent task instead compares OS-disk loss with single versus balanced routing. Actual Portal resources never fail or replicate.
2. **Governance / Benefits governance.** Use/create a group in App Sandbox whose metadata is outside West Europe. Send a new App Service plan request outside West Europe. 4. **PaaS / Service Types.** Choose an actual app on a valid plan, or create its supported dependencies. Inspect app/plan/group. If already read-only, explicitly restore standard first. Edit APP_ENVIRONMENT=staging and CATALOG_MODE=read-only. The Azure-like **Apply in the edit dialog only saves the form draft**; the **Apply on the Environment variables page sends SetAppSettings**. Compare old persisted values before page Apply. Apply read-only, then edit/Apply standard on the same staging app. Inspect both actual receipts and the updated values. Return, reflect and inspect the bounded debrief. The independent variant instead uses two actual apps on one shared plan, a new production/standard target write and a new staging/read-only sibling write, changed target draft and new app-scope reasoning. Neither Apply proves the code read the variables or is running.
