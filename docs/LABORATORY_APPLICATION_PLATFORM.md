# Application Platform — laboratory@3.8.0

Owner scope: build the freely usable resource platform before new course work. This delivery adds a new explicit workspace model. Course-v2 and frozen Laboratory3.0–3.7 remain original authorities. No existing workspace is upgraded, migrated or rescored. No new teaching, assessment, XP or course-linked workspace is introduced.

## Actual supported vertical

A new3.8 workspace can create an App Service Plan, a Web App on that actual plan, a synthetic application configuration and non-secret application settings. The same versioned `execute`/`replay` implementation serves temporary and PostgreSQL modes. Temporary snapshots are client-owned and replay-checked by the server; they are not durable or authenticated evidence. PostgreSQL remains the isolated transactional persistence adapter.

No real hosting, application execution, startup/restart, DNS, global name reservation, network request, health probe, pricing or Azure SKU capacity is simulated. The Web App `enabled` flag is an explicitly modeled configuration flag; there is no measured process state. A latest synthetic deployment determines the bounded configured response. `APP_GREETING` (case-insensitive simulator setting namespace) changes the synthetic text projection only. It is never executed as code or HTML. This is a simulator fixture profile, not generic Node.js behavior.

Azure's application settings can contain secrets; this simulator intentionally does not support that use. It rejects obvious secret/credential field names and recognizable connection-string forms, but this is not a secret detector. Users must never submit real credentials. No credential, password, key, actual database or external connection is generated.

## Authoritative operations and evidence

`CreateAppServicePlan`, `UpdateAppServicePlan`, `DeleteAppServicePlan`, `CreateWebApp`, `UpdateWebApp`, `DeleteWebApp`, `DeploySyntheticApplication`, `SetWebAppSetting` and `DeleteWebAppSetting` are flat typed commands. Complete supported fields are checked; unknown fields and profiles fail closed. Requests retain original identity. The existing repository controls row locking, expected revision, command-ID redelivery, immutable events and commit-before-success. Review runs the same evaluator without committing. Update preserves identity/origin and emits separate `applicationChange.before/after` evidence. Delete never reuses the ID and retains original events. Plan deletion is blocked while referenced. Web App deletion removes only its explicitly owned nested configuration; it does not delete the plan or Resource Group.

Limits: eight plans, twelve apps, twenty-four synthetic deployment records, thirty-two settings, and the existing shared96-entity/512-event budget. Inherited Storage/Networking/Compute/Firewall writes also count application objects. Reset clears all active families, keeps increasing identity allocation and original through-replay history. There is no parallel inventory store.

## Model and database continuation

New `v38` files project the existing topology into a private frozen3.7 validator input and preserve application records around valid inherited operations. All old evaluators/contracts remain byte-identical. Existing requests are replayed using their persisted model, never the latest dispatch. `009-application-platform.sql` only extends model allowlists; it rewrites no rows, World snapshots or receipts.

Cold setup is001→002→009. Existing003–008 installations add009. Repeated current setup is001→002→009. Reapplying a historical narrower constraint after a newer workspace exists is unsupported. Automated actual PostgreSQL tests cover cold and populated3.7 databases, old3.0–3.7 workspaces, repeated setup, immutable receipt access, concurrency, rollback, session isolation and through-replay. Hosted databases/secrets are not provisioned.

## Portal and Architecture Studio

Only3.8 advertises App Services and App Service Plans in the existing shared service catalogue. The same Portal presentation supplies lists, filters, Overview/Properties, parent navigation and Review/Create/Save. The lifecycle editor binds workspace/model/reviewed revision and uses the original Laboratory API. Failed saves never close as a confirmed success. Delete requires exact reviewed configuration and explicit confirmation.

New application inventory rows and Studio relationships derive from the same World. A Web App belongs to its own Resource Group; its actual App Service Plan is a separately labelled hosting dependency, not its ARM parent. Same-subscription cross-Resource-Group hosting preserves both scopes. Nested settings/deployments relate to their owning app. Config analysis is pure/read-only and carries model, revision, resource IDs plus caller workspace. Changed revisions recompute it. A consistent synthetic configuration is not verified reachability, successful deployment or actual runtime.

Tracks B/C are separately developed pure domain modules. They are not advertised in this Portal until their contracts are reviewed and integrated into an explicit model. No Front Door, Application Gateway, database connection or Function runtime is claimed by this application-only vertical.
