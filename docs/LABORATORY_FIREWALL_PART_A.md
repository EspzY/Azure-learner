## Supported resources and commands

- Standard VNet-based Azure Firewall, exact AzureFirewallSubnet, prefix /26 or larger. Firewall and VNet must share Resource Group/subscription/region. Same-region/same-subscription Policy association is a deliberately narrower simulator profile, not a universal Azure restriction.
- Atomic CreateAzureFirewall creates Firewall plus one Standard/Regional/Static IPv4 Public IP configuration resource. The Public IP has a stable ID and relation but no concrete allocated address. Private IP allocation is a synthetic deterministic first-usable-free rule after Azure reserved addresses; it is not a claim about the actual Azure allocation algorithm. No public allocation, SNAT, DNAT or internet reachability is implied.
- Dedicated AzureFirewallSubnet cannot host ordinary NIC/VM resources or an NSG. The profile also excludes UDR on that subnet; onward paths use actual system/peering routes. A VNet has at most one modeled Firewall. Policy has Standard tier and threat intelligence Off; no inheritance or other filtering engines.
- Policy → custom Rule Collection Group → Network Rule Collection → Network Rule. Group and collection priorities100–65000; priorities are unique within each parent in this bounded profile. Allow/Deny belongs to collection, never rule. Network rules use one literal IPv4/canonical prefix/* per source/destination, TCP/UDP and one destination port1–65535 or*. No individual rule priority/action.
- New commands: CreateFirewallPolicy, CreateFirewallRuleCollectionGroup, CreateFirewallNetworkCollection, CreateFirewallNetworkRule, CreateAzureFirewall, CreateFirewallRoute, SetPeeringForwardedTraffic, DeleteRoute. Existing commands remain available under3.5 with all new-family capacity/dependency checks.
- VirtualAppliance routes carry both actual Firewall identity and exact private next-hop IP. Route Table scope/region must match supported Firewall scope; every associated subnet must have a Connected direct peering to the hub. No arbitrary NVA IP. DeleteRoute is an explicit route-only operation, not cascade deletion.
- New peerings default allowForwardedTraffic=false. Explicit Apply changes the _local receiving peering_ setting and records original Apply evidence. Old histories retain their original fields/meaning.

## Analysis composition

Reuse the frozen route candidate construction/LPM/source-priority selector. A private read-only projection substitutes a selection-only placeholder for VirtualAppliance, then restores actual next-hop identity/IP by route ID; it is never persisted or represented as a real None route. Reuse the existing exported NSG evaluateLayer/addressMatch/port rules with their three-valued service-tag behavior. No duplicated NSG matcher.

Supported inspected path is two distinct same-region/same-subscription RFC1918 spoke VNets through one directly peered hub Firewall. Analyse the actual source route, source NIC/subnet outbound NSGs, Firewall group/collection/rule first terminating match, hub onward selected route to the exact destination NIC VNet identity, destination receiving peering forwarding, destination subnet/NIC inbound NSGs, destination return UDR to the same Firewall, hub selected return route to the exact source NIC VNet identity and source receiving peering forwarding. No implicit spoke transit.

Forwarded traffic is checked on Data→Hub for App→Firewall→Data and App→Hub for return. Hub→Spoke settings do not substitute for the receiving spoke setting. A reverse _new connection_ Allow rule is not required for an established response by Azure's stateful filtering principle; this simulator checks return-route configuration only and does not create flow state, send packets or prove a handshake.

No matching supported network rule means default deny within this network-only, threat-intelligence-off profile. Unmatched/unknown NSG tags remain undetermined. None route is a modeled drop. Direct local/peer path is reported as bypassing Firewall. Missing/unequal Firewall return path or unsupported topology is incomplete, never configuration-path success.

Results bind workspace/model/revision, actual NIC/VM/subnet/Firewall/Policy/route/rule IDs, traffic not-sent and connectivity not-verified. Changing World invalidates displayed analysis. Inspection never creates events, receipts, XP or course evidence.

## Conservative IP next-hop prerequisite

A Firewall resource ID is provenance, not an Azure route next hop. Before a positive inspection, both spoke→Firewall private-IP lookups must have an unambiguous selected direct peering route to the exact Firewall hub. Equal remote prefixes, a selected different hub, None or appliance/recursive selection leave the path incomplete. Results expose both lookup routes/errors as well as forward/return destination routes. This deliberately conservative profile does **not** claim that Azure universally recursively applies the full UDR table to a next hop. Microsoft requires direct NVA connectivity but also documents valid broader-prefix NVA configurations; those ambiguous/recursive resolution cases remain unsupported here. A0/0 UDR still loses to a more-specific direct hub prefix. This guard closes an independently reproduced false-positive where two modeled hub Firewalls shared10.0.0.4; original all-command reproduction and source hashes are retained.
