## One engine and one World

`DeliveryState` is designed to be embedded as one slice in the existing versioned Laboratory World. `applyDelivery(state, command, context)` returns an immutable candidate slice, the exact next allocator value, added/updated/removed IDs, target type/scope/region and an existing receipt code. Updates/deletes additionally return before/after configuration. A rejection retains the original slice/allocator and has no changed IDs. There is no mutable inventory, event store, HTTP handler, revision controller, command-ID registry or replay implementation in this component.

The integrating engine must:

1. Build `DeliveryContext` from its actual replay-verified World, never from client-supplied app status. Supply actual group/subscription, VNet/subnet and Web App views, current global `nextId`, total active resource count and command ID.
2. Apply the existing workspace/revision/idempotency/transaction gates. Call the pure component only inside the same original command decision.
3. Commit the candidate slice, allocator, one revision and one original receipt atomically. Preserve before/after evidence and immutable create origin; keep every historical model evaluator frozen. New IDs use the engine's monotonic allocator and are not reused after delete/reset.
4. Include every component record in the global capacity count and explicit reset. Expose `deliveryResources` as a read-only projection and `deliveryReferences` as typed references for Portal/Studio; their IDs resolve the same World records.
5. Check `deliveryDependents` before deleting a referenced Web App, subnet or group. Run `validateDeliveryTopology` against candidate inherited networking changes so a later NIC/VM/Firewall write cannot occupy a dedicated gateway subnet or apply the unsupported subnet NSG/UDR profile.
6. Bind read-only analyses to the actual workspace/model/revision and invalidate prior results after any World change. No analysis creates commands or receipts.

`WebAppView` has an explicit `Microsoft.Web/sites` type and stable identity, actual scope, enabled/public-network/HTTPS configuration, and a declared synthetic application/health path/status. This is a read-only adapter contract with Track A, not another Web App model. The standalone module tests use a clearly labeled adapter unit fixture; they are not positive deployed-World or browser evidence. Existing group/VNet/subnet test parents are created using the actual frozen 3.7 command evaluator.

Additional explicit local restrictions: backends/AFD WAF associations are limited to the same simulated subscription; real Azure supports configurations beyond this profile. Front Door can target a modeled app in a different supported region; it remains global, while Application Gateway is regional. Gateway App Service backends are modeled public endpoints and need not be in the gateway's region. Disabling the app's public network access makes this component's backend path unresolvable; Private Link is not implemented. HTTPS-only app configuration is compatible with both profiles' HTTPS backend forwarding. Source-client routing, backend egress routing, DNS and TLS are outside these configuration checks, so every analysis states `networkPolicy: not-evaluated` and `connectivity: not-verified`.

All analysis results are **configuration conclusions**, never “Connection successful”, VM/application availability, real health-probe telemetry or Azure Network Watcher output. An actual matched WAF rule can give a concrete modeled denial; a positive synthetic application response proves only the declared profile, not reachability or security.

## Resource and input budgets

Use the existing World-wide 96-record budget, counting every record in this slice alongside all existing families. The pure component receives the authoritative total. Local component limits additionally bound four Front Door profiles, four gateways and sixteen records per child collection. Create requests use only exact supported flat string fields (no arbitrary ARM interpreter); field length ≤120 UTF-16 units, well-formed Unicode, no NUL. Path input is a deliberately narrow ASCII absolute-path subset: no query/fragment, percent encoding, `.`/`..` segments, repeated slash or embedded wildcard. Unsupported expressions are rejected instead of ambiguously normalized. Resource names are case-insensitive within the applicable parent/type namespace. IDs come from the caller's monotonic nextId; no random time/UUID or hidden state enters evaluation.
