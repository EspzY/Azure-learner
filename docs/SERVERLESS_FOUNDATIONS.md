## Complete original teaching manuscript

Learner-facing Bokmål copy is maintained in `serverlessNb` in nb.ts. The following is its full authoring specification, not a replacement external reading assignment.

### A — A workload that sleeps between events

A fictional archive receives scanned reports at irregular times. Each new file needs validation and a thumbnail. No file means no thumbnail work. A continuously allocated VM can run this code, but the team then chooses capacity, maintains the guest OS and operates its application process. Paying for allocated VM capacity differs from paying an execution-based meter. Neither option is automatically cheaper: sustained load, reserved capacity, storage, networking and the selected plan change the comparison.

Serverless moves server provisioning and platform operation to the provider, allowing developers to supply code and event configuration. Physical processors, memory, networks and operating systems still execute that code in datacenters. The boundary changes who manages the servers, not whether servers exist. PaaS describes operational responsibility; serverless describes a managed execution/scaling approach. Azure Functions can be both. App Service is managed web hosting; a web application's whole HTTP process differs from a small event handler, although Functions also supports HTTP. Other Azure services, including serverless configurations of Container Apps and Logic Apps workflows, use serverless approaches; Functions is the focal example, not a definition of every service.

Prerequisites: the browser/server chain, physical/virtual computing, provisioning, shared responsibility, consumption and plan-dependent pricing already taught in Cloud Computing. Define event (something happened), trigger (invocation rule), function (customer-authored handler), execution (one invocation of that handler), concurrency (simultaneous executions), cold start (preparation before a new worker can handle code), state (information that must survive an invocation). No unexplained time/capacity arithmetic precedes these definitions.

### B/C — Mechanism, not magic

Event -> trigger -> function execution -> output/result. The uploaded-file event identifies an object; the Blob trigger invokes the handler; customer code validates and creates a thumbnail; a successful output is stored or returned. A configured trigger is not proof of a successful invocation or correct output. Functions has exactly one trigger per function. Optional input/output bindings declaratively connect data to services; code can instead use an SDK. A binding does not remove authentication, permissions or application error handling.

Worked example, separate from the prediction fixture: two queued messages and one execution slot, each job taking one invented round, need two rounds in the warm successful model. There is no throughput/latency claim. The learner's default prediction uses seven events, two slots and two rounds; no preceding text gives its answer. A burst may leave pending work; more configured concurrency changes this bounded model's capacity, not Azure's actual scale algorithm. HTTP/file/timer examples use a common abstract event inbox here, not a claim that all real triggers share queue durability or retry semantics.

### D/E — Azure application and retained responsibility

Use HTTP for a validation endpoint, Blob events for new-file processing, a queue trigger for asynchronous jobs, a timer for scheduled cleanup. A timer is an event source, not an always-running customer VM. The provider operates physical infrastructure, host OS and managed platform. Customers still write/test code, secure application endpoints and dependencies, classify/protect data, configure identities/permissions, triggers, deployment and hosting. A platform update does not repair faulty business logic. External durable storage is needed for information that must survive restarts; local variables are not a durable database. Duplicate/retried delivery and idempotent processing deserve design attention; retries vary by trigger, and this explorer implements no automatic retry guarantee.

### F — Hosting choices, boundaries and counterexamples

Flex Consumption supports event-driven scale and scale-to-zero for on-demand capacity. Optional always-ready instances trade baseline cost for reduced startup delay. Execution/memory meters are not the whole system bill; storage and other services can cost money when code is idle. Premium maintains warm capacity and event-driven scaling, with a minimum billed allocation. Dedicated runs Functions in an App Service plan with allocated capacity, manual/autoscale behavior and appropriate Always On configuration; no universal scale-to-zero or execution-only billing. Cold start depends on plan, readiness, code/dependencies and workload; there is no single Functions startup time. Plan settings, resource limits, quotas and lifecycle interruptions constrain execution. Do not infer that unbounded configurable timeout guarantees uninterrupted execution.

A custom kernel driver requiring guest OS administration is a strong VM case. Long-lived processing is not automatically impossible in Functions: Premium/Dedicated, asynchronous design and Durable Functions can fit some cases. Evaluate process lifecycle, dependencies, latency, operational control and cost. A standard managed web application can fit App Service. Do not teach that Functions replaces all VMs or that serverless means no customer responsibility.

### G — Guided Execution Explorer

Explicit SavvyShark mission explains purpose, prerequisites, observations and boundaries. Close/cancel does nothing; Start enables the guided model. Controls: event kind (upload/HTTP/queue/timer), count0–12, slots1–4, observation rounds1–3, warm/cold/code-error situation. One round is an invented work interval with one job per slot; not seconds, cores, prices or real auto-scaling. Cold reserves the first round for worker preparation. Code-error fails the first attempted job once with no output and no retry. Other selected jobs complete; pending work is distinct from failed work. Counts conserve input = completed + failed + pending. Trace identifies each input, round, trigger, execution and output; text and table provide animation-independent equivalence.

Predict completed jobs before Run; persist input and prediction together, recompute output on replay. Changing a control alone does not overwrite a previous result. Compare a capacity-limited successful run with a cold/error run and explain why the trigger alone cannot ensure successful output. Guided status requires both actual run witnesses and the correct causal explanation; wrong prediction is useful evidence, not a false rejection or fake Azure receipt. SavvyShark first validated run milestone reads the actual recomputed trace, with once-only UI history, reopen and fail-closed storage. No auto milestone in independent or uncertain contexts.

### H — Original independent application

Commit all choices and reasons before any solution/feedback. Scenario A is a variable webhook workload with short independent validation jobs, external state, no guest OS customization and a willingness to evaluate latency/plan. Choose Functions over a guest-managed VM or finished SaaS and justify event-driven customer code. Scenario B is a continuously operated industrial agent needing a vendor kernel driver and OS-level diagnostics; choose VM over Functions or ordinary managed App Service and justify guest OS control. These requirements differ from the guided upload task in trigger/business context and operating constraints, not only names. Additional criteria distinguish trigger from successful output, retained code/data/access duties, and plan-dependent baseline cost.
