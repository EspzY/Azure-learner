# Data & Serverless — bounded domain module

Verified starting point: PR72 `249833f7cb7ea41d3e411444ec3c4f83805d3a5f`, isolated branch `codex/laboratory-data-serverless`. This delivery implements pure resource proposals and read-only analyses under `src/laboratory/data/`. It does **not** register another Laboratory engine, create a database, execute SQL/JavaScript, add a Course Layer or modify any frozen model.

All22 command shapes are flat string fields, at most10 fields, each at most120 UTF-16 units, matching the existing request-envelope boundary. Unsupported fields and missing/inherited fields are rejected. Unknown-field selection uses sorted keys, so JSONB key normalization cannot change which error is returned. No proposal changes its input objects.

No-op updates are rejected. Resource IDs use the engine-supplied monotonic `nextId`, and Updates retain original Create-origin. The result contains changed IDs, before/after configuration and the next allocator value. It is **not** a committed receipt. Only the existing engine/repository may bind revision/command identity, create an immutable technical receipt and commit the proposed World.

## Exact supported profile and limits

The module permits the existing three simulator regions; it does not query Azure SKU availability, regional capacity or quotas. Server names are locally unique per provider in the actual World. A local namespace check never verifies global Azure DNS uniqueness.

PostgreSQL/SQL server names use a conservative lowercase3–63 ASCII alphanumeric/hyphen subset, with alphanumeric ends. SQL in Azure also permits1–2-character names; this profile rejects them explicitly. Database names use a conservative ASCII letter followed by letters/numbers/underscores,1–63 characters. System database names are reserved; the simulator does not fabricate the platform's implicit system databases. Rule/function config names use an ASCII letter followed by alphanumeric/underscore/hyphen, at most60 characters. Plan names exclude underscores, matching the supported ASCII serverfarms subset. Function App names use the Azure sites ASCII2–60 subset. Unicode/Punycode and broader SQL identifier syntax are unsupported. Comparisons are case-insensitive.

Function Apps require an actual StorageV2/Standard_LRS account and a private container in that account. Same subscription and region are required by this bounded Portal profile; cross-RG in the same subscription is supported. The related plan is a separate resource with FC1/Linux identity. Node22, Functions runtime4 and a2048MB profile are fixed metadata, not an allocated worker. No deployment package is uploaded. Only one `GET` or `POST` method and a literal route are supported per HTTP declaration; the route uses the default `/api` prefix during analysis. Anonymous HTTPS is the only HTTP authorization profile. Blob-event analysis takes an explicitly selected existing synthetic textblob from the declared container; it never delivers Event Grid events.

The aggregate World limit remains96 resources/configuration objects. Additional family limits:4 PostgreSQL servers,8 PostgreSQL DBs,4 SQL servers,8 SQL DBs,16 firewall rules,4 Function Apps,16 function declarations and16 database bindings. A Function App consumes two objects atomically. Capacity is checked against the caller's actual whole-World count, not just this module's arrays.

The firewall profile accepts inclusive unicast IPv4 ranges and expressly rejects `0.0.0.0`, malformed/IPv6/CIDR expressions and multicast/reserved high ranges. Azure's special `0.0.0.0` “allow Azure services” semantics are **not** reinterpreted as an ordinary client rule. Private endpoints, delegated subnets, DNS resolution, identity/RBAC, service endpoints, SQL roles/permissions and actual authentication are unsupported.

## Read-only analysis contract

`analyseDatabaseConnection(state, context, {workspace, model, revision}, {connectionId, sourceIp?})` reads an actual binding, source, database, server and server firewall rules. A disabled source or disabled public endpoint yields a concrete configuration denial. An absent hypothetical source IP yields `undetermined/source-egress-ip-unknown`; the module never invents an App Service egress address. A supplied allowed IP plus supported TLS yields only `configuration-consistent`. It never claims authenticated database access, SQL execution or verified network connectivity. Authentication is always marked not evaluated.

`analyseFunctionInvocation(state, context, identity, input)` verifies the actual plan/Storage/container relationships, enabled flags and declared trigger. It returns plain-text synthetic output for a static or echo template. It cannot run supplied code, contact a URL, send an event or mutate a Blob. Missing backing configuration is undetermined rather than fabricated success. All outputs include workspace/model/revision, exact resource references and explicit limitations. Consumers must discard them after any authoritative revision/workspace change.

`dataReferences` derives the actual dependency edges for engine deletion guards and Architecture Studio. Nothing persists a second inventory or relationship index. Source/output references are stable resource IDs, not labels or guessed matching names.

## Integration status and next gate

Implemented and unit-tested: the pure proposal/analysis functions and complete described lifecycle/validation. **Not activated by this branch:** command registration, Laboratory3.8 dispatch, SQL version constraint, HTTP endpoints, Portal forms/catalogue/inventory/Properties/receipts or Studio nodes. Those belong to coordinated TrackA integration, with a new explicit model version and frozen3.0–3.7 preservation. There is no hidden client write path.

The integration must supply `DataContext` directly from the same replay-verified World: actual groups, Storage accounts/containers/blobs, actual Web App projections, other application plans, external dependency references, allocator, original command ID and total resource count. The caller must include `dataReferences` when checking deletions in other modules. It must retain one transaction/revision/receipt authority, existing idempotency and server-side review/stale protection. Reset clears these slices through the same versioned engine while retaining events. A temporary and PostgreSQL workspace must call the same evaluator.

This branch deliberately makes no new Portal/browser/public-persistence claim. It does not satisfy the owner's complete RG→WebApp→database→FrontDoor acceptance journey until the isolated modules pass integration and actual browser gates together. Existing courses, rubrics, technical receipts and v2 World are unchanged.

## Actual verification and retained failures

The harness was corrected so reads are pure and only the explicit command helper advances its counter; the original equality assertion remains. Initial scoped lint found an unused initializer/import and TypeScript found an explicit invalid-input fixture cast requiring `unknown`; these were corrected without suppressions or threshold changes. Subsequent focused results are recorded in the PR/evidence alongside full check, independent audit and exact-head CI, when actually completed.
