## Purpose and learning contract

Implementation delta, 2026-10-23: the owner authorized **Phase 1B.1**, the guided technical subset. Its implemented domain/scenario/replay contract is maintained in [CHAPTER_01_GUIDED.md](CHAPTER_01_GUIDED.md). The full sequence below remains the target; transfer, independent classification, participation award prerequisites and checkpoint promotion belong to Phase 1B.2. See PROJECT_STATUS.md for actual integration/verification, not an assumption that all V01–V16 pass.

A fictional service team needs a custom HTTP application platform without taking responsibility for guest OS maintenance. The learner must choose an appropriate abstraction, establish the right management/lifecycle scope, satisfy a location constraint and construct the actual hosting dependency. A later chapter will deploy/observe application code. Here, successful resource configuration does **not** claim a serving, secure or resilient production application.

| Objective / competency                 | Learner must do                                                                                     | System consequence / evidence                                                                                                |
| -------------------------------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| O1: F01 responsibility and service fit | Choose PaaS for the stated custom-code/no-guest-OS brief; allocate key operational responsibilities | Saved decision/matrix and a counterfactual OS-control explanation; selection changes responsibility view, not infrastructure |
| O2: G01 identity and scope             | Select the application subscription and bind an application resource group under it                 | Valid management relations; tenant identity remains separate; unfamiliar transfer uses a different subscription              |
| O3: F02/G01 geography                  | Predict resource location independently of resource-group metadata                                  | Prediction before result plus plan/app location witnesses; no region hierarchy node or geometry relocation                   |
| O4: G02/C01 hosting dependencies       | Create a supported App Service plan before a web app and choose its reference                       | Plan/app records with typed dependency; missing plan fails without adding an app                                             |
| O5: G03 constraints and correction     | Diagnose a Web-location deny and change the relevant resource configuration                         | Denied receipt and a successful corrected command; explain why changing group metadata is ineffective                        |

Prerequisites: no Azure module completion. Provide optional F00 bridging and an interface tutorial; teach prerequisite concepts within the guided sequence. Experienced learners can choose challenge entry or independent placement and use a labeled reference checkpoint. No user must pass a reading sequence to access controls. Full G/I/N administration is outside this chapter.

Challenge entry starts an unseen transfer variant first. A successful independent submission can satisfy equivalent chapter technical criteria without replaying guided instruction. Offer the failed-experiment explanation after submission rather than forcing a deliberate error during independent work. A failed challenge offers targeted guided practice. After a successful challenge and reflection, its validated world may be explicitly promoted through the same export contract; no assessment world auto-promotes. This route preserves credible experienced-user entry and does not retroactively classify post-feedback work as independent.

Patterns: P02 responsibility comparison, P01 scope/geography, P03 dependency construction, P04 configuration/receipt and P12 transfer. Sources: S01/S02/S03/S04/S05/S07/S12/S38 in [SOURCE_REGISTER.md](SOURCE_REGISTER.md). Proposed outcomes are narrow introductory evidence, not complete coverage of those competencies or any exam.

## Frozen environment and technical limits

Scenario ID `chapter-01`, model set `organization-web@1.0.0`, content/rubric `1.0.0`. Separate variants pin all inputs. All names/IDs/regions/configuration are fictional educational records; there is no Azure SDK, login, endpoint call, deployment or subscription lookup.

| Fixture record              | Guided value / meaning                                                                                                              |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Identity                    | `tenant-lab`, associated with `root-lab`; tenant is not a resource-containment parent                                               |
| Management                  | `root-lab` → optional `mg-lab` → `sub-app` and `sub-shared`                                                                         |
| Subscription labels         | App Sandbox and Shared Sandbox; both readable and available to the chapter's bounded command model                                  |
| Application requirement     | Target subscription `sub-app`; app/group/plan share the application's lifecycle                                                     |
| Group location requirement  | Metadata in `norwayeast`; not a rule forcing resource location                                                                      |
| Resource capability fixture | `norwayeast`, `westeurope`, `northeurope`; one supported Linux learning plan profile, not real SKU/region availability              |
| Custom location assignment  | `policy-web-location` at `sub-app`: only Web plan/app types, allow `westeurope`, deny other locations                               |
| Initial Web resources       | None in guided fixture; no existing generic icon can serve as a valid plan                                                          |
| Limits                      | Three simultaneously created application groups, 16 total active scope/resource records; explicit chapter capacity, not Azure quota |

Group names use the current validated Resource Group name helper and subscription-local uniqueness. Web plan/app names follow an explicit **chapter naming convention** (lowercase letter followed by lowercase letters/digits/hyphens, 3–40 characters). These are training restrictions, not a claim to implement every Azure provider's naming rules. Azure-wide DNS/name availability is not checked. No source response/schema is copied into the simulator.

The custom rule is authored for the chapter, using Resource Manager mode `all`: `type in {Microsoft.Web/serverfarms, Microsoft.Web/sites} AND location not in assignment.allowedLocations` → deny within the assigned subscription. It excludes resource groups by type; it is not the generic built-in Allowed locations policy, a group-location policy or a residency guarantee. Existing resources are not relocated/deleted by a new deny assignment. The model must distinguish current noncompliance from a blocked new operation.

Domain commands are the four serialized command types in [SIMULATION_PLATFORM.md](SIMULATION_PLATFORM.md#narrow-serialized-contracts). `CreateWebApp` derives location/OS from its referenced supported plan; it does not take an independently editable app-region field. Missing plan is rejected. Cross-resource-group plan hosting is **unsupported in this first model**, rather than falsely labeled invalid in Azure. `DeleteEmptyGroup` supports empty groups only; nonempty/cascade deletion is explicitly unsupported. No change-group-metadata command, resource move, role assignment, runtime deployment, autoscaling, zone configuration or full ARM execution.

Creation commands are separate transitions, not an atomic multi-resource deployment. A failed app creation leaves an earlier plan/group. Group metadata, plan region and app location stay visible independently. Receipt wording says configuration registered in the simulation; health and code delivery are unassessed.

## Full guided sequence

The interface remains one workspace. The sequence constrains learning prerequisites, not every exploratory click. A learner can inspect other components and see supported commands at any time; scenario goals advance only from evidence predicates. Each stage names what to notice and invites an experiment. No camera movement or selection counts as completion.

The responsibility model for this **custom PaaS app** assigns physical host and underlying OS to Microsoft; custom application code/configuration and identity/data protection/access decisions to the customer. Grade critical responsibility choices using row IDs, not screen position. Shared/service-specific nuances are explained rather than forcing every security responsibility into one owner checkbox.

## Independent transfer specification

Two materially different authored variants support replay after solution exposure. Both permit operational tools and official source references (independent open-book); no worked solution, autofill or instructional next-step hints before submission. The interface may explain how a control works without disclosing the technical answer. No time limit or command-count penalty.

| Variant                   | Initial condition / changed constraint                                                                                                                     | Required decision and observable success                                                                                                                   | Transfer failure it detects                                                                                                                                                                |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `transfer-scope-location` | Fresh scaffold; target `sub-shared`; group metadata must be `westeurope`; Web policy in that subscription allows only `northeurope`                        | Bind a group in the changed subscription, create plan there in North Europe and an app using it; predict and explain independent metadata/hosting location | Blind copying of guided subscription or West Europe plan fails requirements/policy. Names are not the answer.                                                                              |
| `transfer-existing-plan`  | Precreated application group in `sub-app`, metadata `norwayeast`; existing Linux plan in `westeurope`; a newly active Web policy allows only `northeurope` | Recognize that the old plan remains but would give the new app a denied location; create a new supported plan in North Europe and bind the new app to it   | Treating group region as the fix, assuming policy moves the old plan, or assuming any existing plan satisfies the app request. Existing noncompliant plan is preserved and clearly marked. |

Variant fixtures are pinned, not random failures. Assessment requires a **pre-feedback** placement prediction, a structured hosting/metadata causal reason, the valid target state and a responsibility counterfactual: a workload requiring guest-OS modification changes the suitability of the PaaS choice. A short free explanation may supplement these observations but is not automatically graded.

For the first independent attempt, choose one variant deterministically from an authored ordering based on exposure history. Retry of a revealed variant is practice. Offer the other as unseen only if not already exposed; once both are revealed, say no unseen variant remains. A later new version needs reviewed new constraints, not just renamed resources. Successful transfer supports the named narrow outcomes, not complete F/G/C mastery.

## Rubric and participation

### Authoring and state-machine bindings

The first runner can be small, but the chapter must be data-driven. Store the stage/variant/constraint/role bindings in a typed serializable definition. The following names are proposed stable keys, not existing runtime handlers:

| Stage ID         | Enter / advance condition                                                                              | Registered evaluator/data binding                                                             |
| ---------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| `orient`         | Fresh guided attempt → `responsibility`; challenge entry → `transfer` child attempt                    | Variant/mode selected, model boundary acknowledged                                            |
| `responsibility` | Decision rows submitted; guided correction remains in this stage until critical rows fit the brief     | `responsibility-fit@1`, requirements `custom-code` + `no-guest-os`                            |
| `organize`       | A group is explicitly bound under the target subscription with the required metadata location          | `group-in-target-scope@1`, role `application-group` and variant constraints                   |
| `build`          | Prediction saved, a deny witness observed in guided work/probe fork, and valid plan/app bindings exist | `web-hosting-valid@1`, `resource-location-policy@1`; roles `hosting-plan` / `application`     |
| `explain`        | Structured causal reasons submitted; all guided predicates met                                         | `location-cause@1`, `policy-remedy@1`                                                         |
| `transfer`       | Frozen child attempt submitted, irrespective of pass/fail                                              | Five-criterion rubric; hint/variant exposure attached before classification                   |
| `review`         | Findings reviewed; launch optional practice as a **new attempt**, then return here                     | Immutable submission references; no retroactive score editing                                 |
| `reflect`        | Structured counterfactual/reflection submitted                                                         | Participation prerequisites and export validity evaluated separately                          |
| `finish`         | Completion summary displayed                                                                           | Stable award deduplication; optional explicit promotion only if technical export criteria met |

Guided order is `orient → responsibility → organize → build → explain → transfer → review → reflect → finish`. Challenge entry is `orient → transfer → review → reflect → finish`; a failed challenge can launch a new guided workspace rather than rewriting its result. Required-stage graph is acyclic; free inspection/back navigation is presentation state, and retries/forks are new attempt instances. Criterion truth is recomputed from current bindings/receipts, never latched by clicking a step. If a previously satisfied requirement is invalidated, withhold completion/promotion and identify the unmet predicate.

Variant constraint binding is explicit: guided `{ targetSubscription: sub-app, metadataRegion: norwayeast, allowedWebRegions: [westeurope] }`; transfer-scope-location `{ targetSubscription: sub-shared, metadataRegion: westeurope, allowedWebRegions: [northeurope] }`; transfer-existing-plan `{ targetSubscription: sub-app, metadataRegion: norwayeast, allowedWebRegions: [northeurope], initialPlanRegion: westeurope }`. A role-binding decision contains an entity ID, not a name-derived lookup. No evaluator reads selected camera nodes or text labels.

Predictions/reasons use stable semantic IDs, including `metadata-independent`, `plan-determines-app-location`, `policy-targets-resource-location` and `guest-os-control-changes-service-fit`, plus original distractor IDs. Those IDs select reviewed explanations and criteria; they are not accepted as arbitrary truth from untrusted storage. A submitted attempt's command/decision record is revalidated before constructing evidence. Optional free prose remains human-review-pending.

### Criterion findings

| Criterion                | Machine witness                                                                                                                            | Interpretation                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------ |
| `service-responsibility` | Correct critical responsibility rows and OS-control counterfactual before transfer feedback                                                | Introductory service-boundary understanding      |
| `management-scope`       | Exported group is under variant target subscription; app/plan bound to its lifecycle group                                                 | Applied scope choice                             |
| `hosting-dependency`     | App references an existing supported plan; both location/configuration are valid for the fixture                                           | Dependency construction                          |
| `geography-cause`        | Pre-result prediction and structured reason identify metadata independence and plan-derived app location                                   | Concept applied beyond the initial demonstration |
| `constraint-response`    | Final resources meet the variant policy; causal reason identifies the relevant configuration and rejects metadata relocation as the remedy | Requirement/policy distinction and correction    |

Guided technical completion requires all five guided predicates after feedback/correction and an observed deny counterexample. Transfer reports each criterion separately; **independently demonstrated in this task** requires all five met, no teaching hint/solution before submission and a previously unseen variant. Otherwise report assisted, needs practice or incomplete evidence, retaining the actual findings. Do not infer motivation or intelligence from failure. Human review is needed for the optional rationale and whether the task actually discriminates understanding.

Proposed participation rule: once per learner, stable award ID `chapter-01-participation`, **100 XP** after technical chapter completion (guided, or equivalent successful challenge entry), transfer submission (pass not required when guided technical completion already exists) and reflection submission. This rewards meaningful participation; a failed transfer remains visibly failed. No points for clicking, hints, changing lenses, repeat attempts or checkpoint promotion. Existing 80/40 legacy awards remain intact but the new runner does not emit them for reused primitives. Content/model patches retain the same award ID. XP does not unlock independent proficiency or certification readiness.

## Persistent world handoff

After guided technical completion or equivalent successful challenge entry, the learner may promote a validated workspace as `application-platform@1.0.0`. Show the exact diff and exported roles: `identity`, `target-subscription`, `application-group`, `hosting-plan`, `application`. IDs/names are bound by reference, never inferred from a magic string. Persist model/source versions, parent checkpoint revision and `learner` provenance. Additional supported sandbox records may remain visible; they are not silently deleted or assessed.

The next engineering chapter can consume these roles through a compatibility adapter, add a reviewed network/diagnostic fixture and reuse the same application scope. A learner without this checkpoint can take a labeled reference version. An incident fork cannot damage the main checkpoint. Restore/replay selects the original pinned revision; promote never rewrites history. This chapter demonstrates the first persistent-world evolution, not a complete long-running estate engine.

## Visual and accessible interaction specification

Keep the dark identity, dimensional overview, concise contextual inspector and native/list/XYFlow alternatives. Add a responsibility comparison lens and a deployment receipt/diff lens; preserve selected entity/attempt across switches. Plan and app need distinct readable labels and a dependency relation different from containment. Location comparison shows group metadata beside plan/app location with a textual causal statement. The denied plan is shown as a rejected command marker, never as an existing healthy object.

Desktop: compact objective/requirement HUD, scene in the middle, inspector/command drawer, receipt tray and switchable matrix. Collapse irrelevant layers when a decision is active. Mobile: one primary lens at a time, persistent objective summary, touch-sized action controls and a contextual bottom sheet. Required selected object/action must remain visible; use list → configuration → receipt when the scene would occlude it. No long lesson article and no precision wiring gesture. Native forms/table controls, explicit labels, heading/landmark order, status announcements and focus on new resource/receipt provide the complete loop. Reduced motion removes transition, not information. Sources/glossary/accessibility controls do not count as teaching hints.

## Content/engineering complexity and implementation brief

Estimate **medium bounded chapter complexity**, not a delivery schedule: five connected outcomes; one responsibility matrix; three fixtures (guided + two transfer); four command types; two resource models; one custom location-policy subset; one receipt/diff projection; five rubric criteria; one checkpoint export. Reuse the existing scene, inspector/dialog, localization, group name/uniqueness helpers and repeat-safe progression principles. Preserve legacy tests/behavior through an adapter while separating new state and awards.

Do not first build an abstract service/plugin catalog, full identity/network engine or every future evidence feature. Keep content typed/versioned and UI independent of exact mission IDs. Use this chapter to discover the smallest reusable runner; Phase 1C generalizes only after authoring/review evidence. Human learning/performance assumptions in this document remain untested until Phase 1B.

Recommended Phase 1B instruction after review: implement only `chapter-01@1.0.0` against V01–V16, the five criterion rubric and the declared model boundary; preserve the legacy vertical slice and existing routes; keep all learner copy in nb.ts; show actual decisions, denial/correction, transfer and checkpoint promotion; run required checks/screenshots and conduct/record the professional review exercises. Stop and record a source-backed discrepancy instead of broadening Azure behavior silently. Do not start B/C, accounts, live Azure or a generic platform refactor.
