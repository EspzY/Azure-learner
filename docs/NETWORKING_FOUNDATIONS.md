- Ordinary peering needs nonoverlapping IP ranges and both sides Connected. Peering itself is nontransitive; configured NVA/service chaining/gateway transit are distinct mechanisms, not an automatic exception applied by this model.
- Newer subnet peering selects participating subnet lists rather than all VNet subnets. Current documentation requires subscription allowlisting and lists CLI/PowerShell/API/ARM/Terraform configuration, not Portal support. Teach its bounded scope; do not invent an operative Portal button or assume all peering has identical subnet reach.
- The full current subnet-peering limitations section additionally permits reuse of nonparticipating address spaces only under documented uniqueness across participating spaces/links. It records over-advertised routes, delegated-subnet, AVNM and VM-generation qualifications. A visible route is not proof of delivered traffic. Our single-address-space fixture is deliberately more restrictive; it is not a complete subnet-peering eligibility validator.
- Private DNS zone resolution needs the relevant VNet link or an explicitly configured resolution mechanism. Forward resolution between linked VNets does not itself require application peering. A link is not application routing or authorization. Azure-provided default host resolution is not universal cross-VNet/custom-zone DNS.
- DNS Private Resolver's inbound/outbound endpoints and forwarding rulesets have explicit prerequisites. Merely selecting its name cannot create hybrid connectivity. P07's VPN/ExpressRoute operational understanding is not credited here.
- VM network overview contains legacy/default public-IP/outbound details. These are not adopted as current universal defaults or implemented resource fields. The local authoritative model has no NIC address allocation or outbound traffic.
