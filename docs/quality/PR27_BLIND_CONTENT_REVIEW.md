## MAJOR BC-01 — cp12 rejects a technically defensible ACI explanation

**Evidence:** `src/content/nb.ts:9319`, `:9327`, `:9332`, `:9345`; `src/domain/curriculum/compute-items.ts:40`–`:48`, evaluator at `:67`–`:76`.

The case explicitly permits an on-demand finite container group. Decision 3 is ACI. Reason 3 states that a manually triggered job has a running lifecycle that ends when the container task finishes. This is not exclusive to Container Apps Jobs: an ACI run-once task can also stop when its process finishes with an appropriate restart policy. Microsoft's [ACI run-once/restart-policy documentation](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-restart-policy) explicitly documents this task lifecycle and external result storage. Its current nonzero-exit restart caveat also prevents inventing an unconditional exactly-once guarantee.

The key accepts zero-based `[0,2]` and `[2,0]` but rejects `[2,2]`. The feedback says reason 3 does not establish ACI having the same job management or retry configuration. Neither such assertion appears in the selected reason. A learner can therefore give a relevant, technically true explanation and receive an incompatible-pair failure. This ambiguity was independently identified before seeing the key.

**Concrete correction:** make reason 3 state the property that actually distinguishes the candidate: a reusable Container Apps Job configuration is distinct from each execution started manually; an execution can finish while the job definition remains available for another start. This follows Microsoft's [Jobs concepts and manual execution documentation](https://learn.microsoft.com/en-us/azure/container-apps/jobs). Keep ACI's reason about directly creating the container group. Then make feedback reject cross-pairing because it describes a different resource/configuration lifecycle, not because the learner supposedly claimed retries. Alternatively, keep the current generic sentence, accept `[2,2]`, and explain the shared run-to-completion property without implying identical management features.

**Executed evidence:** `node --experimental-strip-types --input-type=module -e` imported `evaluateCompute` from the actual file and evaluated the three relevant pairs. Exit 0: ACI/generic lifecycle returned `decision:true, relation:false` and `compute.cp12.incompatible.2.2`; ACI/ACI-specific reason and Job/generic lifecycle both returned `relation:true`.

## MAJOR BC-03 — Systematic answer cues make paired reasoning largely eliminable

**Evidence:** `nb.ts:8968`–`:8971`, `:9001`–`:9004`, `:9034`–`:9037`, `:9066`–`:9069`, `:9131`–`:9134`, `:9164`–`:9167`, `:9263`–`:9266`, `:9296`–`:9299`, `:9329`–`:9332`, `:9362`–`:9365`, `:9395`–`:9398`; further prompt cues at `:9121`, `:9185`–`:9189`.

Across the bank, correct reasons are sober, qualified causal statements. Competing reasons repeatedly say that all services are identical, everything is automatic, a VM cannot process events, a registry synchronizes every runtime file, a resource group creates physical RAM, a disk proves backup, or a local receipt proves secure application operation. These choices are not consistently plausible alternatives for the stated case. cp11 and cp12 additionally let the learner match service names in the reason to service names in the decision. cp06 explicitly names the absent relation; cp08's title and premise already identify the resource to investigate.

This is a bank-wide quality finding, not a claim based on a learner study or a measured guessing percentage. A cautious-reader heuristic can eliminate the extraordinary assurances and often identify the lone answer that restates the premise. Rotating positions does not address semantic cues. Such first attempts do not adequately discriminate the intended causal understanding.

**Concrete correction:** author competing rationales that are technically true within different, explicitly distinguishable constraints; make the learner use the supplied facts to select the relevant reason. Examples: for event processing, compare retained application responsibility with a VM's genuine OS-control benefit and AVD's genuine interactive delivery benefit; for FD/UD, offer a real mitigation for the wrong failure type; for memory, distinguish a size increase, an application-memory investigation and extra storage using observations that make one immediate action defensible. Do not make one answer uniquely verbose or uniquely hedged. Remove answer-revealing titles and direct diagnoses from the item. Recheck every decision×reason combination for partial truth and avoid penalizing a true relevant explanation merely because it is not the author's preferred wording. Keep counterfactual feedback tied to the exact offered claim.

Replacements must still preserve clear constraints and the explicit service/plan qualifications; replacing magical distractors with several simultaneously correct choices without updating accepted pairs is not a fix.

## MAJOR BC-04 — cp05 treats ordinary availability-set placement as a known zone

**Evidence:** `nb.ts:9088` says the VMs are in the same zone and an availability set; `:9104` tells the learner to read that explicit placement. Related teaching labels are `:8222`–`:8224` and `:8393`. `docs/COMPUTE_HOSTING.md:108` does disclose that the model's chosen zone0 is not an actual nonzonal lookup, but that qualification is absent from the independent item's own premise.

The FD-versus-UD answer is defensible under a stipulated abstract model. The item's known-zone description is nevertheless an unsupported ordinary Azure placement premise. Microsoft's [orchestration comparison](https://learn.microsoft.com/en-us/azure/virtual-machine-scale-sets/virtual-machine-scale-sets-orchestration-modes) distinguishes availability-set FD/UD from explicit zonal assignment. The [SAP planning guide](https://learn.microsoft.com/en-us/azure/sap/workloads/planning-guide) documents ordinary zone/set assignment exclusivity and also a qualified proximity-placement-group combination. Therefore this review does **not** assert that physical co-location in a zone is universally impossible. The defect is presenting known zonal placement without declaring such a special premise or identifying the situation as a hypothetical model.

**Concrete correction:** say the VMs are in the same region, their inspected FD values differ and their UD values match; no zonal separation or actual zone assignment is provided. Ask which planned/unplanned effects these facts support. Keep the correct FD/UD distinction, and do not use the availability-set name to infer an AZ. In the teaching/model label, say that a common hypothetical physical-failure boundary is declared for this example and that actual nonzonal AZ placement remains unknown. The model may retain an explicitly fictional failure demonstration; it must not teach an operative Azure zone/set combination through shorthand.
