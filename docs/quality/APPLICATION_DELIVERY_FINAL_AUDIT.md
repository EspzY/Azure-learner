## Current Azure source checks

All pages below were independently opened and relevant actual body text read on **9 November 2026**. Microsoft Learn displayed an authorization notice in page chrome, but also supplied the relevant complete public article/schema text; no access control was bypassed.

- [AFD route matching](https://learn.microsoft.com/en-us/azure/frontdoor/front-door-route-matching): exact before wildcard, final slash-prefixed wildcard and case-insensitive patterns agree with implementation. The selected endpoint is explicit; DNS/custom-domain/TLS/cache/rulesets remain outside scope.
- [AFD probes](https://learn.microsoft.com/en-us/azure/frontdoor/health-probes): HEAD/GET, 200 criterion, sampled real health and all-origin fallback. The module inspects declared synthetic health-path/status configuration, sends no probes and does not infer application-path success or sampled availability.
- [AFD custom WAF rules](https://learn.microsoft.com/en-us/azure/web-application-firewall/afds/waf-front-door-custom-rules): unique ascending priorities and terminating Allow/Block match the bounded one-condition model. [Official PowerShell guidance](https://learn.microsoft.com/en-us/azure/web-application-firewall/afds/waf-front-door-custom-rules-powershell) explicitly supports Standard custom rules and endpoint association through a profile security policy. The [ARM association schema](https://learn.microsoft.com/en-us/azure/templates/microsoft.cdn/profiles/securitypolicies) confirms actual parent/policy/domain relationships; custom-rule records are correctly labeled nested local configuration, not ARM top-level resources. [Policy modes](https://learn.microsoft.com/en-us/azure/web-application-firewall/afds/waf-front-door-policy-settings) distinguish Detection logging from Prevention action. This module evaluates one endpoint-wide policy, not the newer multiple-scope precedence feature.
- [Gateway components](https://learn.microsoft.com/en-us/azure/application-gateway/configuration-overview) and [request rules](https://learn.microsoft.com/en-us/azure/application-gateway/configuration-request-routing-rules): listener → Basic rule → pool/backend setting, setting-associated custom probe, and unique 1–20000 priority agree with code. HTTP frontend and HTTPS/443 App Service backend are deliberately limited; no certificate or live gateway health is claimed.
- [Private gateway deployment](https://learn.microsoft.com/en-us/azure/application-gateway/application-gateway-private-deployment): private-only v2 without a public IP is supported in the opt-in network-isolation experience. `networkIsolation: true` is documented simulator metadata, not a fabricated ARM property or completed real feature registration.
- [Gateway infrastructure](https://learn.microsoft.com/en-us/azure/application-gateway/configuration-infrastructure): dedicated subnet, reserved addresses and high-end private frontend address are grounded. `/24` is an Azure recommendation, not a universal minimum. One gateway per subnet, `/24` or larger, and no subnet NSG/UDR are explicitly conservative module restrictions. Scaling and general IP allocation remain unimplemented.
- [Naming rules](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/resource-name-rules) and [route ARM schema](https://learn.microsoft.com/en-us/azure/templates/microsoft.cdn/profiles/afdendpoints/routes): provider-specific characters and parent hierarchy were checked; the smaller name/field limits and local endpoint uniqueness do not claim global Azure name availability.
