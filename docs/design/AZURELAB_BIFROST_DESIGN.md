## Stable integration API

- Add `.bifrost-learning` to the actual learning or landing surface. Every supplied `--bfc-*` value is scoped there; `html[data-bf-theme='light'|'dark']` selects values only inside those wrappers. It does not put colors or a font on html/body. Do not use a learning wrapper to recolor operational Portal descendants.
- Import `ThemeToggle` from `src/features/design/theme.tsx`; optional `className`. The compact native select offers system/light/dark. The root `BifrostThemeProvider` owns only the dedicated `azurelab.visual-theme.v1` preference. Blocked/failed readback is shown once inline, with no toast or false saved claim.
- Import `BifrostBrandMark` from `src/features/design/brand-mark.tsx`; optional `className`, `title`. Without title it is decorative. All path data, transforms, viewBox and fills are exactly the supplied **landing** SVG; `useId` only makes its internal base reference unique.
- Fonts: `--bf-font-satoshi` and `--bf-font-open-sans`. The heading stack asks for installed Satoshi, then the actual local Open Sans fallback. Body uses local Open Sans. `--bf-radius=4px`, `--bf-radius-lg=8px`, `--bf-space-1…10` and `--bf-focus-ring` are shared presentation primitives. Success/warning/alert use their paired `-fade`/`-fade-c`; info uses theme pairs. Color alone never supplies status meaning.

The synchronous head loader reads only the visual key and sets only `data-bf-theme` before paint. Server/first-client control markup is stable; a scoped system media fallback also works without JavaScript. It never writes storage on load. Valid external visual-key changes and system changes update appearance; blocked storage still permits an in-memory selection. Existing provider nesting/order is preserved exactly, with the visual provider immediately around AppShell.
