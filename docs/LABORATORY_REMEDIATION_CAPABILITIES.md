The subnet-NSG contract currently offers association/replacement with an existing compatible NSG, not a separate remove command. Do not infer operations from a visible resource or from Azure's real service capabilities. Association validation, resource/event budgets and model/version restrictions still apply.

## Priorities for a bounded follow-up

1. Implemented in3.6: custom NSG and nested Firewall network rule Update/Delete with stable identity and immutable before/after evidence. Standard NSG rules remain read-only. Collections/groups/policies cannot be edited or deleted; action/priority stay at collection level. Existing3.0–3.5 workspaces are not upgraded and remain create-only for these rules. See [Security remediation contract](LABORATORY_SECURITY_REMEDIATION_PART_A.md).
2. Topology remediation: peering removal/configuration lifecycle and clear route replacement/association semantics. Current3.5/3.6 can delete/recreate a UDR and apply forwarding, so those narrower remediation scenarios are feasible now.
3. Resource organization/Compute lifecycle: explicit move/replace/delete contracts with dependency safety before promising large customer modernization exercises.
4. Storage lifecycle and optional advanced networking later, scoped to approved real operations.

This matrix distinguishes implemented3.6 rule lifecycle operations from future lifecycle proposals; it does not authorize broader changes. A customer task must be rejected as not operationally solvable when its required remediation exceeds this matrix. Reset alone is not a credible substitute for resource-level modernization.
