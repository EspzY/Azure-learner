The subnet-NSG contract currently offers association/replacement with an existing compatible NSG, not a separate remove command. Do not infer operations from a visible resource or from Azure's real service capabilities. Association validation, resource/event budgets and model/version restrictions still apply.

## Priorities for a bounded follow-up

1. Network-security remediation: explicit versioned update/delete/replace of custom NSG and Firewall network rules/collections, retaining original through evidence. Today a learner can identify an overbroad rule but cannot remove or safely narrow it.
2. Topology remediation: peering removal/configuration lifecycle and clear route replacement/association semantics. Current3.5 can delete/recreate a UDR and apply forwarding, so those narrower remediation scenarios are feasible now.
3. Resource organization/Compute lifecycle: explicit move/replace/delete contracts with dependency safety before promising large customer modernization exercises.
4. Storage lifecycle and optional advanced networking later, scoped to approved real operations.

This is a capability/prioritization document, not authorization or implementation of these changes. A customer task must be rejected as not operationally solvable when its required remediation exceeds this matrix. Reset alone is not a credible substitute for resource-level modernization.
