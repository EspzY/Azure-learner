## Bounded operative design

VNet → multiple contained, nonoverlapping IPv4 subnets; independent regional NSG → create-only custom security rules → authoritative subnet association. IDs share the same monotonic allocator as Storage; all views derive from the same verified World. No packet evaluation, IP allocation, NIC/VM association, peering, UDR, firewall, real Azure API or general delete/cascade.

The simulator initially accepts one **RFC1918** IPv4 block per VNet, prefix/8–/29 and wholly within one private range; Azure also supports other address spaces. Subnets use canonical network addresses/8–/29 within their VNet; Azure's five reserved addresses are informational metadata, never allocated addresses. Separate disconnected VNets may overlap. Names follow the documented bounded ASCII Microsoft.Network rules and case-insensitive resource namespaces. Platform-reserved service subnet names are unsupported.

NSG custom priorities100–4096 are unique **per direction**, names unique within the NSG. First scope: Inbound/Outbound, Tcp/Udp/Any, Allow/Deny, one canonical IPv4/CIDR or wildcard per source/destination, and a single port0–65535 or wildcard per source/destination port. No service tags/ASGs/lists/ranges in custom rules. Azure's six standard rules are read-only reference configuration, separated from custom rules and never falsely evaluated. Association requires equal region and subscription, permits different RGs, and one NSG per subnet. Reassociation is an explicit Apply with a new original receipt.

Official sources, exact limits, test evidence, capabilities and independent review are completed alongside implementation. No external database or credentials/Vercel changes are authorized. Local PostgreSQL and isolated CI remain authoritative; public503 without configured database is an accepted deployment limit.
