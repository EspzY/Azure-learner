## Three alternatives evaluated

Scores are implementing-author design judgments (1 weak–5 strong), **not measured learning results**. Compare a complete representative sequence, not just attractive stills.

| Criterion                     | A: directed technical narrative       | B: persistent infrastructure workbench | C: explanation + bounded experiment                           |
| ----------------------------- | ------------------------------------- | -------------------------------------- | ------------------------------------------------------------- |
| Beginner comprehension        | 4: explicit order, passive risk       | 2: discovery needs a mental model      | 5: explanation immediately beside its mechanism               |
| Accuracy/depth                | 4: caveats may interrupt pacing       | 5: properties remain inspectable       | 5: full manuscript plus local constraints                     |
| Visual clarity/cognitive load | 4: one focus, transient history       | 2: many controls/components exposed    | 4: one variable; progressive reveal                           |
| Interaction quality           | 3: advancing can replace thinking     | 5: genuine construction                | 5: predict/run/compare/explain                                |
| Reuse/maintenance             | 3: authored sequences for every topic | 3: requires broader model up front     | 4: small topic presenters + shared explanation/result pattern |
| Accessibility                 | 4: needs manual/history parity        | 3: spatial alternative needed          | 5: HTML controls, table, deterministic steps                  |
| Desktop/integration           | 4: fits course, animation competes    | 4: fits Portal but too early           | 5: embeds next to existing lesson/lab lifecycle               |

Select **C**. Use A's contextual narrative/attention direction and B's stable physical system, but do not expose a general simulator before teaching its vocabulary. C allows the learner to stop, read, change one assumption, inspect the result and compare a prior run. It prevents the renderer becoming educational truth. The risk is still overloading a split workspace: limit one primary question and one result, put optional derivation behind an explicit disclosure, and validate with beginners. No WebGL, remote artwork, timeline framework or new dependency is needed.

## Shared visual grammar

Use the course's light reading surface, ink/navy technical diagrams and restrained blue/cyan accents. This is not the archived neon game identity. Diagram labels use system fonts; no remote fonts/assets. Minimum essential label14px, reading16–18px, line-height1.5–1.65; captions at least13px. Heading/term/quantity hierarchy must be consistent. Readable prose measure55–75 characters; technical board gets the larger column.

| Token / convention                             | Semantic use                                                                                                           |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Paper `#f7f9fc`, white surface, ink `#172f48`  | Reading ground, neutral existing objects; navy board only when labels maintain contrast                                |
| Blue `#075fa9` / lighter outline               | Selected object/focus, never failure; keyboard focus also has offset outline                                           |
| Teal `#087b78` on pale teal                    | Served work / accepted modeled result, with explicit text                                                              |
| Amber `#965019` on pale amber + diagonal hatch | Unmet/requested-but-not-served work, with counts; never an existing deployed object                                    |
| Slate `#65758a` + unfilled dashed shape        | Unused allocated capacity, distinct from absent/failed capacity                                                        |
| Thin solid line + membership label             | Management containment only                                                                                            |
| Directed labelled line                         | Request, hosting dependency or control action has an explicit type; never reuse one unlabeled arrow for all three      |
| Chassis outline / software bands / scope bands | Physical infrastructure / executable software / management grouping, respectively; colour alone never defines the kind |

Put labels on/next to their objects, not in a remote legend alone. Read selected detail beside the board; don't cover the object with a tooltip. Values include units and period names. Show requested configuration and last **executed** result separately; editing must mark an old result stale or remove it. Difference annotations reference both runs' assumptions. Selection/inspection is not a technical operation.

Transitions last roughly150–250ms and represent a state change, never an invented deployment timer. Reduced motion shows the same result immediately. No looping packets, decorative parallax, auto-advance or hidden result on a countdown. Route navigation/history remains native; core illustrations do not need pan/zoom. If later dense diagrams need zoom, retain fit/reset and semantic list access. No arbitrary dragging is essential.

Desktop is the permanent product priority:1920×1080 primary,1440×900 secondary,1366×768 minimum. Persistent explanation beside board at these sizes; allow normal document scroll for long prose. Do not shrink labels to fit. Baseline small-screen flow remains usable, but no new mobile system or mobile acceptance gallery is introduced.

One composition carries the shop request, selectable physical/server software illustration, invented unit definition, simple worked period and changed campaign prediction/run/compare. Original inline SVG geometry is code-owned; no downloaded art. HTML controls drive a pure bounded calculator. It deliberately stops before virtualization, cloud provisioning, naming or module assessment: those are storyboard/handoff specifications, not fake playable widgets.

What it establishes: feasibility of a steady explanatory workspace, explicit unit labels, before-result prediction and synchronized causal output without touching authoritative learning state. What it cannot establish: beginner comprehension, a reviewed complete module, retained understanding, expert visual acceptance or real Azure performance. Capture/readability and human review gates are recorded in PROJECT_STATUS.

## Visual acceptance review

At each desktop size, inspect initial system, component selection, unit/worked case, committed prediction and changed-capacity result. The title/control/result and labels must be readable without overlap, selected component must match the explanation, and bars/tiles must conserve demand/capacity. View at browser zoom200% using normal document scroll. Keyboard follows explanation→controls→result/table; error is announced and focus stays operable. Screen-reader text must name objects/units independent of SVG. A beautiful frame with unexplained squares or a result that updates before Run fails review. Human art/learning/accessibility review stays outstanding until actual reviewers participate.
