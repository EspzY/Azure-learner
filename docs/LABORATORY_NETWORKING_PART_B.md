## Bounded networking semantics

Peering is create-only, one named local→remote relation; no self/duplicate pair, missing parent or overlapping VNet address space. Both VNets must exist in this authenticated workspace. Same/cross local subscription and any of the three supported public-cloud regions are allowed, without claiming Entra/RBAC or cross-cloud support. `Initiated`/`Connected` is derived from the actual absence/presence of a reciprocal relation. Virtual-network access is enabled in this sole supported profile; forwarded traffic, gateway transit, Route Server and advanced peering flags are rejected, not decorative controls. No transitive route export through a hub.

Regional route tables belong to an existing group/subscription. Routes have a unique case-insensitive name and unique canonical IPv4 prefix per table; duplicate prefixes are explicitly outside this profile. Supported UDR next-hop values are ARM `VnetLocal`, `Internet`, `None`. No appliance/gateway/peering/service-endpoint next-hop input, IP parameters, tags, BGP or IPv6. One active route table per subnet, multiple subnets per table, equal subscription/region but potentially different groups. Explicit reassociation/disassociation produces original commands/receipts. A `VnetLocal` route must be contained in every associated VNet; this is a conservative simulator constraint, enforced both when adding a route and associating a table, not a universal Azure API restriction. Unassociated tables may be prepared before association.

All existing VNet/subnet/Storage/NSG limits remain. New local caps:16directional peerings,8route tables,32UDRs overall/16per table, with the shared96-object ceiling. These are simulator budgets, not Azure quotas. No general delete/update/cascade is added.

## Read-only route analysis

Analysis uses a verified current server World, source subnet and strict unicast destination IPv4. It is a deterministic projection, not an authoritative result store, command or receipt. It records workspace/model/revision/through identity and exposes candidates, prefix matches, exact selection reasons and original UDR/peering references. A newer World invalidates the displayed analysis until explicitly recalculated.

Model local VNet routes, direct reciprocal-connected peer ranges, documented default routes and the source subnet's associated UDRs. Use longest matching prefix first; at equal prefix User overrides System. BGP-preference and service-endpoint exceptions are explicitly unsupported because neither capability exists in this World. Never sort UDR before a more-specific system route. Pending one-direction peers are excluded with a reason; peers-of-peers never become candidates. No separate subnet-local system prefix is invented.

The current Microsoft default table includes0.0.0.0/0→Internet and None routes for10/8,172.16/12,192.168/16,100.64/10,157.59/16,127/8,104.147/16,104.146/17. An exact local VNet range replaces its equal None prefix. Host/platform addresses outside the supported unicast profile, including168.63.129.16, are explicitly unanalysable, not assigned a false UDR result. VNet profile remains Part A's one RFC1918 range. Internet next hop does not prove public egress or Azure-service path; no default-outbound access, NAT, service-endpoint or platform-traffic assumption is inferred.

UI distinguishes **route calculated**, **configured next hop**, and **traffic not evaluated**. There is no verified-connection status, packet/NSG evaluation, VM/NIC effective routes or Network Watcher claim. In particular, App↔Hub and Data↔Hub do not establish App↔Data; a UDR does not create a missing appliance, gateway, peer or working return path.
