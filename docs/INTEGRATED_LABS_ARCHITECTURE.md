## Actual persistence and assessment constraints

The durable prefix is captured on the first normal technical write. Before any such write, a newly mounted current consumer may reread valid archived Chapter work. After sandbox.v2 exists, archived edits never silently rebase it. Legacy raw keys are never written by the new stores. Four versioned Web handlers retain the original parser/policy helpers; tests preserve frozen-prefix receipts while explicitly enlarging v2 capacity. The current inventory is partitioned, not mirrored.

One prior technical/SaaS attempt is retained on reset. Submitted practical records can be re-evaluated against that archive; an active session cannot keep modifying an archived world. Beyond retained history, references become visibly unverifiable and answers remain stored. Export before repeated resets. Independent pre-submission criteria are hidden; explicit help reveals guidance and marks aid. The course temporarily presents the active task instead of exposing theory implicitly; choosing teaching or journal help is classified. First results are not overwritten by retry.

Benefits inspection bridges are allowlisted navigation context only. They open actual VM/configuration/receipt/policy/architecture views and preserve exact module/topic return; they create no session completion, XP or synthetic operational metric. The optional full lab is a separate explicit action.

Guided reasoning choices are disclosed after actual configuration and required inspection. Independent requirements remain fixed after requesting help. The source/persistence logic cannot be advanced by a tab visit, animation, navigation URL or mascot action.

An explicit in-lab reset abandons an active practical session and starts a new session against the new technical attempt. Earlier submissions and assistance remain in history. A guided PaaS reset reactivates the existing prerequisite Web guide. An externally invalidated context is visibly unverifiable and offers an explicit fresh attempt; it never silently becomes successful. SaaS guidance derives its current action from validated outcomes (capacity rejection, seat release/assignment, departure, sharing, data review and history inspection). Submitted debriefs project the actual replayed configuration; they store no second resource inventory.
