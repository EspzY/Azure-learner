Material source reconciliation:

- VPN Learn's broad statements that traffic crosses the internet and authentication uses a preshared key must not become universal rules. Product documentation distinguishes on-premises S2S/P2S internet transport from encrypted VNet-to-VNet communication over Microsoft's network. Current topology/P2S material documents certificate, Entra ID and RADIUS options with protocol/client constraints. Teach these distinctions without implementing authentication.
- ExpressRoute provides private transport, not automatic cryptographic protection. Default circuit traffic is not encrypted. MACsec is optional ExpressRoute Direct link protection; IPsec can protect an end-to-end VPN path. These are distinct scopes, and TLS remains a separate application choice. No encryption configuration is executed.
- ExpressRoute private peering reaches VNet resources; Microsoft peering serves eligible Microsoft public-service addresses under its requirements. Neither is Part A VNet Peering. Do not turn Learn's simplified global-connectivity wording into a universal entitlement: circuit SKU, geography, service and provider requirements matter. Global Reach connects on-premises sites; Premium's geographical reach is a separate qualification.
- Built-in circuit redundancy is not independent end-to-end failure isolation. Customer edge, last mile, provider, peering location, gateway and application each have failure boundaries. A compatible, explicitly routed S2S VPN may back up private-peering VNet connectivity; it does not automatically back up every Microsoft-peering service. No guaranteed failover time, SLA, throughput or current price is simulated.
- A Private Endpoint is a private NIC in the consumer VNet targeting a supported service subresource. Approved state, appropriate regional/VNet placement, route and DNS matter. It does not move the managed service into the subnet, expose every subresource, authorize every user, or automatically disable public network access. Storage explicitly documents the latter separation. Service-specific limitations remain visible.
- Public addressability is not anonymous data access. Network firewall/public-network settings and identity/data authorization are separate. DNS can resolve an otherwise rejected public endpoint. Private addresses similarly provide no universal authorization.
- Private DNS records and client resolver visibility/forwarding must match the service. For a shared zone, required client VNets need links; on-premises clients need a reachable resolver/forwarder path. Do not query Azure's internal DNS IP directly from an arbitrary external network. No private-link hostname or IP is inserted into real Sandbox resources.

## Original manuscript — authored before presentation

### From connected networks to a usable service

A manufacturing organization has an office network, travelling engineers and a managed catalogue in Azure. They face different problems: joining a whole office network, connecting one laptop, choosing a transport route and selecting the catalogue's entry point. A VNet organizes Azure addresses; it does not itself connect the office, encrypt a path, resolve the intended endpoint or grant a database role. Part B examines those decisions one layer at a time. A model success means declared educational requirements match, not that a packet, login or application response occurred.

### VPN Gateway: encrypting a defined connection

A VPN carries traffic inside an encrypted tunnel over an underlying network. Azure VPN Gateway terminates supported tunnel connections at a VNet gateway. Site-to-site joins an office VPN device to the gateway using IPsec/IKE over the public internet; point-to-site starts from one supported client device and does not require an office VPN appliance. VNet-to-VNet uses VPN gateways to encrypt communication between Azure networks over Microsoft's network. That differs from ordinary VNet Peering, which establishes direct Azure network connectivity without a VPN gateway. A whole-site design is not fixed by installing a client on one laptop.

Gateway resources and compatible address/routing/device settings are prerequisites, not proof of a working application. The GatewaySubnet is dedicated to the gateway; it is not the ordinary VM subnet from Part A. Client protocols and authentication choices have compatibility constraints. Several tunnels share gateway capacity, and gateway SKU/region/feature limits must be verified for implementation. Current overview recommends AZ gateway SKUs and marks older VpnGw1–5 for migration; this course does not recommend a live SKU or promise a throughput. Encryption cannot repair a failed internet underlay, an absent route or an application's missing permission.

### ExpressRoute: private transport and separate security

ExpressRoute extends an on-premises network into Microsoft's cloud through private provider connectivity. Provider-based service requires coordination among the organization, connectivity provider and Microsoft; Direct is a distinct option for appropriate deployments. A logical circuit, provider provisioning, appropriate peering, routes and VNet gateway association are different dependencies. Private peering addresses VNet connectivity; Microsoft peering addresses eligible public-service connectivity and has separate requirements. Both differ from VNet Peering.

Avoiding public-internet transit can meet a transport-policy requirement and improve predictability, but it is not a performance or availability guarantee. Compare provider charges, circuit/gateway and data-transfer terms, geography, lead time, expected demand and support responsibilities, rather than invented currency totals. ExpressRoute is not encrypted by default. MACsec on Direct protects physical link scope; IPsec and application TLS solve different protection requirements. A service can still reject an authorized network path at application authorization.

For resilience, trace the customer edge, access circuit/provider, peering location and Azure dependencies. Two logical paths sharing the same failed edge are not independent. VPN backup is useful only when a compatible tunnel, routable prefixes, underlay and routing preference are actually planned. The deterministic scenario declares a configured usable backup; it does not simulate Azure failover algorithms or promise restoration time.

### Public and private endpoints: where the request enters

An endpoint is a service entry point used by a client. A public endpoint uses public addressing; a service can still require authentication, data-plane roles and permitted network sources. Public does not mean anonymous. An allowed firewall source does not grant a database role; a valid role does not bypass a disabled public entry point.

A Private Endpoint is a consumer-side network interface with a private subnet address linked to a supported target service/subresource through Private Link. The managed service remains managed by its provider; it has not become a VM in the subnet. A Pending or wrong-subresource connection is different from Approved access to the intended subresource. Network reach can come from the same or suitably connected VNet and properly connected on-premises networks, subject to routing and policy. Public network access remains a separate service setting. Storage's public firewall controls the public endpoint; it must not be falsely applied as a universal private-endpoint firewall rule. Product-specific policy and authorization remain necessary.

### DNS and Private Link: choose the address, then test the path

The usual service hostname can resolve through a private-link name to a private A-record when the client's resolver sees the relevant private zone. Without the correct view, a client may obtain a public address or no address. A zone existing somewhere is insufficient: the client's linked VNet or working forwarding/resolver path matters. On-premises DNS needs a reachable, appropriately configured Azure resolver/forwarder path. Use the service's normal hostname and supported connection settings; do not universally replace connection strings with privatelink aliases or raw IPs, which can break expected host/certificate behavior.

The Explorer exposes hostname → DNS result → chosen public/private entry → declared route → endpoint approval/network policy → application authorization → assumed service response. Correct DNS cannot supply a missing route; a route cannot approve a Pending endpoint; an Approved private entry cannot grant an application role. A wrong-address diagnosis and an authorization diagnosis require different corrections. All example addresses and service responses are explicit fixtures, never actual allocated Sandbox values.

## Guided learning and assessment design

1. **Choose a hybrid plan:** an office needs a non-public transport path, provider readiness and separate payload protection. Contrast an internet VPN with provider ExpressRoute and then inspect encryption scope. Require prediction, saved outcome and a causal choice.
2. **Diagnose a hybrid outage:** a failed provider link and a declared compatible S2S backup require separate underlay and routing checks. Contrast a successful configured backup with a shared failed office edge; no automatic Azure routing operation is claimed.
3. **Inspect the service entry:** compare an authenticated public API with an Approved private endpoint while independently toggling public network access. Observe that adding a private entry does not close the public entry or grant application rights.
4. **Resolve the private destination:** investigate a client whose DNS view selects the public entry while public access is disabled. Correct zone/resolver visibility, then remove its declared private route or application permission and explain why the remaining failure changed layers.

Independent cases must change actor, failure boundary or decision structure, not rename these scenarios. At least twelve original decision/reason cases cover a roaming client, a whole branch, gateway encryption versus peering, provider migration, encryption scope, backup limitations, authenticated public access, remaining public exposure, Pending approval, custom/hybrid DNS, service hostname/server-identity contract and service subresource scope. A technical choice with an incompatible reason fails. First/help/retry/abandon and prior family exposure remain separate; all interpretations are local and unauthenticated. No readiness percentage or new XP.
