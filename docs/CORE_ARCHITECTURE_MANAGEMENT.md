## Original teaching manuscript

### A — Organization before vocabulary (CA04–07)

Nordlys Drift develops a booking application. Its development team experiments daily; its production team owns a customer-facing service; a separate platform team maintains shared infrastructure. Without deliberate organization, a valid resource can be created under the wrong budget, a shared component can be removed with a temporary experiment, and a broad control can affect teams that were not considered. A list of region names cannot solve these administrative problems.

Azure separates administrative scope, identity and physical placement. Scope answers which resources an administrative assignment can reach. Identity answers which principal is requesting access. Region and Availability Zone describe physical placement/failure boundaries. These structures interact, but none is a synonym for another. We will trace actual AzureLab resources, compare relations and investigate a deliberately bounded rule before returning to supported Portal work.

Prerequisites: physical servers/virtualization, service responsibility, Part A region/zone distinction and the difference between local configuration and a running application. Worked example: two development APIs may share a lifecycle; a production database should not be grouped with a short-lived demo merely because both use West Europe. Independent tasks change the team's constraints and ask for reasons, not the example's names.

### B — Resources and providers (CA04)

An Azure resource is an individually managed instance represented through Azure Resource Manager. A virtual machine, its managed disk, a virtual network, an App Service plan and a Web App are different resource types. Resource Manager is the management layer; a resource provider implements operations for its service. Microsoft.Compute/virtualMachines identifies a provider namespace and type, not an actual machine name. Microsoft.Web/sites represents Web Apps; Microsoft.Web/serverfarms represents App Service plans. A provider/type describes what kind of object can be managed, while the resource ID identifies a particular object in its scope.

Configuration is not operational proof. A locally accepted AzureLab VM bundle records modelled dependencies; it does not boot an OS or establish network traffic. A Web App linked to a plan records its supported hosting configuration; it does not prove that code is deployed or healthy. In real Azure, management/control-plane operations and service/data-plane use are distinct. AzureLab does neither against Azure: all supported operations and receipts remain local.

The workload resources supported here belong to resource groups. Do not turn this teaching simplification into a universal claim: resource groups, subscriptions and management groups themselves are ARM resource types, and some Azure resource types exist at higher scopes. Nested child resources, such as a subnet under a virtual network, do not mean that resource groups can nest. Investigate type, administrative parent and dependency separately.

Worked example: an API's Web App depends on its App Service plan. The group contains both for administration. A membership edge says where an object is managed; a hosting edge says what it needs. Real Azure permits some cross-group dependencies when a service supports them; this simulator deliberately restricts its Web hosting to the same group. That restriction is not a universal Azure rule.

### C — Resource groups and lifecycle (CA04)

A Resource group is a container for related resources inside one subscription. For supported workload resources, each belongs to one group at a time. Groups are siblings under their subscription; a group cannot contain another resource group. Grouping gives a useful management boundary for operations, scoped access and relevant policy assignments. It does not automatically give all users access, inherit tags or create resource dependencies.

Common lifecycle means resources are expected to be created, changed and retired together. A temporary demonstration's app and dedicated plan can share a group. A shared network serving several long-lived workloads often requires a different lifecycle and explicit dependency planning. Group membership is not a guarantee that every resource must always be removed together. In real Azure, deleting a group requests deletion of its contents; locks, backup data, permissions and cross-group dependencies can prevent or complicate completion. AzureLab supports only its declared empty-group deletion, not a general cascade-delete exercise.

A group's Region stores metadata about the group. It does not force each member's resource location. Resources in one group may use different supported regions. For example, a group's metadata can be Norway East while its App Service plan and Web App use West Europe. That says nothing about zonal redundancy. Current ARM documentation describes metadata request rerouting during regional disruption; do not infer application availability, recovery timing or data location from metadata location alone.

Counterexample: putting a VM and unrelated temporary experiment in one group because both use North Europe confuses geography with lifecycle. Conversely, putting a Web App in a group does not create a hosting plan; the real supported hosting reference must exist. Our hierarchy shows membership, while the relationship perspective exposes hosting and VM dependencies.

### D — Subscriptions, costs and identity (CA05)

A subscription is an administrative boundary for resource organization, governance, usage accounting and service limits. Resource groups belong to subscriptions. An organization can use several subscriptions to separate workloads, environments, responsibilities or scale requirements. A technically valid name and region do not compensate for choosing the wrong subscription: the resource would enter a different administrative and cost context.

A subscription trusts one Microsoft Entra tenant for identity. A tenant can be associated with several subscriptions. A directory contains identities; it is not a billing account, a resource group or a physical datacenter. Billing accounts, profiles and invoice sections depend on the commercial agreement. A subscription tracks usage, but one subscription does not universally imply one separate invoice. Changing a directory association is not the same as changing billing ownership. No login, billing, directory transfer or permission administration is implemented here.

Two subscriptions can contain resources in the same region; one subscription can contain resources in several regions. Administrative isolation does not configure physical failure separation, routing or replication. Select the right subscription first, then the group and supported resource configuration. App Sandbox and Shared Sandbox are AzureLab's actual training scopes, not production subscriptions or a full enterprise landing zone.

Worked example: a platform team's shared utility must use its designated shared subscription even when the application subscription would also accept the resource technically. The independent task supplies a different team's explicit production requirement, so a correct solution must explain organizational context rather than merely pass name validation.

### E — Management groups and root (CA06)

Management groups organize multiple subscriptions under shared governance scopes. They can contain other management groups and subscriptions. A management group or subscription has one parent in this hierarchy; a management group can have multiple children. Resources are reached through their subscriptions and groups, not placed physically inside a management group. Moving or nesting administrative scopes is not an AzureLab operation.

A tenant has one Tenant root management group above its management groups and subscriptions. Directory and root are shown together for orientation, but the directory is an identity context and root is a management group. AzureLab's root-lab ID is a local simplification; in real Azure the root group's ID corresponds to the tenant ID. Azure roles and Entra roles are distinct; being a directory administrator does not by itself mean every resource operation is granted. We do not model role assignments.

Assignments at a management group can reach descendants, making common controls easier to apply consistently. That breadth also increases impact. A control intended for one development subscription should not casually be assigned at root. Organize groups around justified governance needs; do not mechanically reproduce an organization chart or make regions the hierarchy. Current landing-zone recommendations favor a shallow, deliberate hierarchy. Such recommendations are design guidance, not a rule that Azure permits only one organizational pattern.

Counterexample: two subscriptions under Learning share an administrative ancestor. This does not establish a common network, grant access to every user or spread their resources across Availability Zones. The actual Web location policy in AzureLab is assigned to App Sandbox, not Learning or root. Its sibling Shared Sandbox is not covered by that particular assignment.

### F — Trace the complete hierarchy (CA07)

Read the model from identity context to management scopes: Microsoft Entra directory → Tenant root management group → management groups → subscriptions → resource groups → resources. The first arrow expresses directory association; the remaining administrative arrows express scope ancestry or membership. A resource's provider/type and its physical location are properties, not replacement management parents.

In the Management Hierarchy perspective, select an actual group and trace its subscription and ancestors. In Resource Relationships, inspect a Web App's plan or a VM's supported disk/network chain. A hosting edge does not imply management inheritance. Geography is a third perspective taught in Part A: a region is not a subscription's child or parent. All three can describe the same resource without becoming the same relationship.

The explorer reads current replayed inventory. Empty groups and subscriptions remain visible even when no application exists. Creating a valid group or supported app in the ordinary Portal updates this projection; a rejected command must not add a node. If saved simulator data is uncertain, the lesson says so and withholds an authoritative observation rather than inventing a resource. Selecting or expanding a node is navigation, not understanding or assessment credit.

### G — Scope is necessary, not sufficient (CA06–07)

A policy definition describes a condition and effect. An assignment attaches a definition to a scope. Descendants can fall inside that assignment's administrative reach; exclusions and exemptions can qualify this in real Azure. Applicability still depends on rule conditions, mode, target type and other parameters. A rule limited to Microsoft.Web/serverfarms does not automatically reject a virtual machine simply because both are under the same subscription.

An effect determines consequence when its conditions match. In our conceptual create-request model, audit reports a finding without blocking, deny would reject the matching noncompliant request, and disabled does not evaluate it. These are deliberately limited examples, not a complete Azure Policy evaluator, compliance scan, remediation process or permissions model. Existing resources are not automatically deleted by a deny assignment. Overlapping assignments are evaluated according to their rules, not replaced by the nearest child rule.

AzureLab's actual custom Web location deny is assigned to App Sandbox, targets its supported plan and app types and allows West Europe. A group's metadata location is not the checked Web resource location. An actual rejected receipt reports the assignment scope, requested location and unchanged inventory. Shared Sandbox is outside this assignment. The hypothetical comparison can move a rule to Learning, target a different type or change effect, but never writes policies, resources or receipts into the simulator.

Guided investigation: predict how many fixture resources a proposed rule would reject, run the pure model, inspect per-resource ancestry/type/location/effect, then compare with a different assignment. Explain why being in scope does not guarantee denial. Finally start the existing PaaS lab explicitly, inspect its real subscription/group, actual rejection/correction and hosting relation, and return to the scope unit. Existing valid lab work can be reused honestly; it never becomes a new independent score.

## Independent assessment manuscript and acceptance

Four original cases use two decisions each (configuration/choice plus causal reason), with plausible distinct alternatives and specific post-submission explanations:

A: A logistics production team has a formally designated production subscription; a development subscription accepts the same technical resource. Select production and explain the administrative/cost boundary rather than region or naming.
B: A retiring campaign app uses an existing plan that continues hosting two other applications. Decide its independent grouping and explain shared-consumer lifetime versus metadata location. Unlike the worked dedicated-plan example, the hosting dependency must survive the app. Real Azure can host across groups when service constraints hold; the bounded local create-lab requires the same group and does not demonstrate that operation.
C: Two sibling management-group branches each contain a subscription. A VM-only deny is assigned to one branch. Analyze a compliant VM within that branch, a nonmatching Web plan within it, and a region-condition-matching VM outside it. None is denied by that exact rule, for three different reasons. This changes ancestry depth, target type, effect and condition structure from the guided parent-audit comparison; it is not the actual App Sandbox deny.
D: A hospital needs resistance to one physical zone incident. Correctly distinguish administrative subscriptions/groups from separate zone placement and a complete dependency/redundancy design. Match directory identity, root/group scope, group membership and physical location without treating them as equivalent.

All eight criterion IDs map to CA04–07. No worked answer is shown before first submission. Opening teaching, Summary or either shared Journal while active records help; old aid rules also shield assessments in other modules. First/help/retry/abandon are separate replayed observations. Corrected retry does not become first unaided. Completion requires actual teaching checks, guided model comparison/explanation and live-resource investigation; independent results remain separately visible per objective. No new XP, Microsoft Learn completion or exam-pass inference.
