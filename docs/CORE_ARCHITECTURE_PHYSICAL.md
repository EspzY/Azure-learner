## Original teaching manuscript

### A — From a virtual machine to the building

An archive application is still executed by physical processors and memory, even when its owners provision only a virtual resource. A datacenter is the facility supporting racks of servers, storage equipment and network connections. Compute runs instructions; storage retains information; networking carries communication between components. These are related dependencies, not three names for a VM. Virtualization shares and isolates physical capacity, as taught earlier; it does not remove the host or building.

The facility also depends on power, heat removal, connectivity and controlled physical access. Redundant equipment and operational procedures reduce some risks. They do not imply that every application has a second independent copy. A building-level outage can affect colocated components together: separate VM names, resource groups or subscriptions do not establish physical fault separation. A fault boundary is the scope within which a particular modeled incident has a shared effect. A host fault, facility failure, zone failure and regional incident are different scopes. Physical security reduces unauthorized access risk; it does not make customer code correct or demonstrate compliance for a workload.

Worked example: a report API and its data copy share a fictional facility. If its power boundary fails, both are unavailable in the model. Putting a second API in another building can preserve a process, yet requests still fail if the only data copy was lost. Availability is an end-to-end property of the configured dependency chain. We do not simulate actual power systems or individual Azure buildings.

### B — Geography and region are placement concepts

An Azure region is a localized collection of datacenters and network infrastructure. A geography groups regions for data-residency boundaries. They are not ARM management parents: a resource group can contain resources deployed to different regions, and its metadata location does not make those resources physically colocated. Some services are nonregional; do not force every service into a single region diagram.

Multiple regions let teams choose proximity, required capabilities and physical separation. Distance can influence latency, but this is not a latency calculator. Region selection requires checking the actual service, tier, capacity, dependencies and contractual data-handling requirements. An attractive region name alone proves neither legal compliance nor complete data residency, including backups, logs and support processing.

Reviewed examples, not a live catalogue: Europe contains West Europe and North Europe; Norway contains Norway East and Norway West; Italy contains Italy North. The current list identifies zones for Norway East and not Norway West, and Norway West has restricted access. Italy North has zones and no paired region. "Europe" as a continent and Azure's specific geography labels must not be conflated. The schematic does not reveal coordinates, actual buildings or Azure's private resource placement.

### C — Zones and the deployment decision

Availability Zones are separated groups of one or more datacenters inside a region, with independent power, cooling and networking infrastructure. A region with zone support provides multiple distinct fault boundaries. The zone is not necessarily one building, and a resource instance is not itself a zone. Region zone count, zones used by a service and replica count can differ.

A zonal resource is pinned to one logical zone. It can be isolated from a failure elsewhere, while remaining vulnerable to its own zone failing. Several customer-managed zonal resources distributed between zones require appropriate routing, data replication and recovery design. A zone-redundant service distributes its components across zones and manages its supported zone recovery; check the service's actual guarantees/configuration. Some services enable this automatically, others require an explicit configuration. App Service zone redundancy, for example, depends on supported plan/configuration and infrastructure; the existing AzureLab plan creation does not implement it.

Nonzonal/regional deployment does not promise a selectable zone or zone resilience. Its undisclosed placement could be affected by a zone incident. In the model, unknown placement yields an uncertain result for a smaller failure, rather than pretending a resource is safely elsewhere. Not all regions support zones; not every service, SKU or tier supports them in every zone-enabled region.

Logical zone numbers belong to a subscription's mapping. Zone1 in two subscriptions can refer to different physical zones. The diagram uses fictional physical labels A/B/C and an explicit example mapping, never a universal map of Azure. A second subscription is an administrative distinction, not proof of a separate building or fault boundary.

### D — Pairing is a relationship, not a configured recovery system

Microsoft assigns some regions a paired region. Some services use that relationship for geo-replication or aspects of disaster recovery; it is not an application dependency, replication setting or live failover connection. North Europe and West Europe are a documented symmetric pair. Italy North is nonpaired. Brazil South points to South Central US, while South Central US points elsewhere: pairing can be asymmetric and can cross geography boundaries.

A regional incident can affect all zones in that region. A multi-region application requires appropriate alternate capacity, data handling, traffic routing, dependencies and tested recovery. A service's built-in capability may perform some of that work; two region names alone perform none. You can design with paired or nonpaired regions when the chosen services and requirements allow it. Region pairing can influence selected services and platform recovery/update behavior; it does not guarantee automatic replication/failover for every resource, zero data loss or a recovery time. The explorer intentionally keeps its region-pair annotation separate from configurable replica/dependency edges.

### E — Separate cloud environments and sovereignty

Azure public cloud, Azure Government and Azure operated by21Vianet in China have different operational boundaries. Azure Government serves eligible US government organizations/partners through an isolated US environment. Azure in China is a physically separated instance operated independently by21Vianet. Endpoints, eligibility and available services/features can differ; a normal public-cloud subscription cannot simply select an environment as though changing its resource region. Azure public cloud also offers controls supporting sovereignty requirements. Sovereignty is broader than isolation, and a European region is not a synonym for Azure Government.

Choose from actual legal, operational and application requirements with qualified review. Do not infer safety, residency or compliance merely from "sovereign", the geography label or encryption alone. Confirm permitted data/replica locations, identity/access, service behavior and applicable terms. The course offers a technical comparison, not legal advice, account setup, a guarantee or an exhaustive sovereign-product catalogue.

## Infrastructure Explorer: authored model contract

Learner controls: geography/primary example region; placement (single, same-zone separate facilities, multizone, multiregion, nonzonal); secondary example region when applicable; single/replicated data; primary-only/healthy-app routing; failure scope and explicit target; committed prediction. Configuration inspection changes no result/evidence until explicit Run. The selected geography filters primary region choices only; multi-region can cross that geography, with an explicit boundary warning rather than an invented prohibition.

Synthetic topology: three illustrated zones where documented supported, each with two fictional facilities; otherwise two fictional unzoned facilities. This is an original explanatory fixture, not an actual Azure datacenter inventory, count, address, topology, SKU capability or subscription mapping. Every component has an explicit region/zone/facility placement or an explicit unknown placement. Facility failure only affects that facility; zone failure affects its facilities; region failure affects all its components. Unknown nonzonal placement remains unknown under a smaller incident. Replicas are explicit, logically equivalent, ready at the observation boundary only when selected. No time, consistency, corruption, quorum, bandwidth, SLA, probability, real service health or automatic recovery timing is modeled.

Each API copy requires an available declared data copy and configured routing. Primary-only routing does not switch when another app survives. Healthy routing can select surviving app copies, but cannot restore a missing data dependency. Result derives from components and relations. Uncertainty is retained instead of manufacturing successful availability. Multiregion does not follow the pair relationship automatically. A region without zones cannot accept a zonal placement or zone failure target. Invalid combinations report validation failure and cannot create a result.

Guided sequence: predict and run a single-facility loss; compare an app spread with one vulnerable data copy; explicitly replicate data and route to surviving app copies under a zone failure. Three distinct recomputed witnesses plus a correct dependency explanation support guided practice. Merely inspecting a region, changing a selector, starting a mission or showing a milestone does not. Region-scale and nonpaired/unknown-placement cases remain available to investigate. The prediction commits with input and remains distinguishable from observed result after controls change or reload.

SavvyShark: native mission with explicit start/cancel; factual current task/location/reason/expected/observed guide; two versioned read-only milestones (single-boundary loss; preserved usable path). Only a new qualifying saved run in safe guided context can claim automatic display. Persistent PR20 UI history prevents reload/navigation repeats; manual recall remains available for actual qualifying history. Corrupt/denied history suppresses auto and warns; active/uncertain independent contexts close/discard explanation intents. No modal stacking or technical/evidence effect from visibility. Explicit, confirmed recovery clears only invalid/unknown Part A storage and preserves all other keys.
